## 2 形成性研究脚本（每场 30–40 分钟）

统一提示：「请按平常的方式使用，想说什么就说什么；卡住了也继续尝试，我会记录。」
主持人只复述问题，不教操作。

| # | 任务 | 成功判据（观察，不看代码） | 记录项 |
| --- | --- | --- | --- |
| T1 | 找到一段适合自己水平的视频并开始逐句学习 | 进入观看页且字幕与当前句可见 | 成功/失败、耗时、求助次数、放弃点 |
| T2 | 在字幕里查一个生词并把它保存到词库 | 词卡打开、词出现在词库 | 同上，附使用的入口（画面词 / 文稿词） |
| T3 | 在复习里找到刚保存的词并完成一轮训练 | 进入复习并完成至少一题 | 同上，附是否误入「真题」 |
| T4 | 做一组听写并看懂结果里的逐词差异 | 提交并看到结果页 | 同上，附是否理解「漏听/多写/听错」 |
| T5 | 打开一套真题，提交后找到某题的解析 | 结果页出现解析位 | 同上；解析缺失/占位时记录原话 |

**每次会话必须记录**：任务成功与否、耗时、求助次数与内容、退出原因、原话摘录（匿名编号 U1…Un）。
失败不是「用户不会用」的同义词——先判断是文案、可见性、还是流程本身。

## 3 单项体验实验（每轮只验证一个假设）

### 3.1 本轮假设（H1）

> 在观看页词卡里提供「来源句 + 回看原句」之后，用户在「查词后回到原句重听」上的求助次数与耗时下降。

选择它的理由：它已经有了实现（词卡来源行、「回看原句」），能用 A12 的既有事件与行为数据测量，
不需要新增功能面；且属于 A15 刚刚提取过的「字幕与查词动作」边界，回滚成本低。

### 3.2 预注册口径（先写死，不能事后挑指标）

| 项 | 内容 |
| --- | --- |
| 实验单位 | 用户（不是会话） |
| 分组 | 对照 = 词卡不显示「回看原句」；实验 = 显示（同一版本、同一入口，仅按钮可见性差异） |
| 主指标 | 「查词后 10 秒内回到同一句并触发重听」的比例（事件：`gloss_open` → `replay` 同 `flow_id`） |
| 护栏 | 页面错误率、词卡关闭率、观看页跳出、每用户查词次数（不得因按钮显著下降） |
| 窗口 | 至少 14 天；两组各自 ≥100 名有查词行为的用户再分析；不足则延长而不是缩小样本 |
| 排除 | 内部账号、机器人流量、无 `flow_id` 的旧客户端事件 |
| 决策规则 | 主指标提升 ≥5 个百分点且护栏无恶化 → 保留；主指标无差异或护栏恶化 → 撤回按钮；介于两者 → 继续观察一轮 |

### 3.3 技术要求

- 主指标依赖的两个事件已于 2026-11-01 接线：`gloss_open` 在词卡打开时发一次并带本次词卡自己的
  `flow_id`；`replay` 在原句重听发起时发一次，若距该次查词 ≤10 秒且同一句就带同一个 `flow_id`。
  契约版本随之从 v2 升到 v3（`backend/app/services/event_contract.py`、前端
  `frontend/src/lib/analytics.ts`、[`metrics.md`](../comprehensive-audit-2026-10-29/metrics.md) 三处同步）。
- 事件定义与版本必须同时更新 `backend/app/services/event_contract.py`、前端 `lib/analytics.ts` 与
  `metrics.md`；不得把新事件直接塞进 `MEANINGFUL_EVENT_TYPES` 改变旧分母。
- 分析脚本与 SQL 随实验一起提交，结果与样本量一起报告；小样本不报百分比结论。
- 实验仍未开始：这里是「事件已可用」，不是「实验已在跑」。上线后需要先积累至少两周有
  `gloss_open` 的样本，才能按 3.2 的分组与窗口分析。
