## 3. 高危发现（P0 优先修复）

### A. 安全：两个可直接利用的漏洞

**A1. 上传存储型 XSS → 账户接管（HIGH）✅ 已人工复核**
- `backend/app/services/upload_service.py:24-47` + `backend/app/api/v1/media.py:226-300` + `backend/app/main.py:198-200`
- 上传视频时：Content-Type 白名单校验的是客户端可控的请求头；**落盘扩展名取自攻击者控制的 filename**（`upload_service.py:43`）。上传 `x.html`（Content-Type 伪装 `video/mp4`）→ 写入 `media/uploads/{uuid}.html`。`upload_temp_dir = ./media/uploads` 位于 `local_media_path = ./media` 之下，文件**立即可经 `GET /media/uploads/{uuid}.html` 访问**；serve_media 按扩展名返回 `text/html`，且安全头中间件跳过全部 `/media`（main.py:198-200，无 nosniff/CSP）。攻击者可在受信源站投递任意 HTML/JS，读取 localStorage 的 `seeword_token`/`seeword_refresh_token`（7 天有效）→ 完整账户接管。后续管线改名 `_stage_local_upload` 还保留 `.html` 扩展名（video_processing.py:170-178）。任意注册用户可投毒，受害者点开链接即中招。
- 修复：扩展名改为服务端白名单推导（同头像上传）+ Content-Type 由扩展名反推 + 魔数嗅探；/media 响应加 `X-Content-Type-Options: nosniff`；上传后清洗非媒体文件。

**A2. /media/proxy 未认证 SSRF（HIGH）✅ 已人工复核**
- `backend/app/api/v1/media.py:73-84,108-152`
- `GET /media/proxy` 无认证。主机后缀白名单（含 `aliyuncs.com`）**只校验初始 URL**，但共享 httpx 客户端 `follow_redirects=True, max_redirects=3`——302 跳转目标不再校验。攻击链：自有 OSS bucket（域名匹配 aliyuncs.com 后缀）+ OSS 回源重定向规则 → `/media/proxy?url=https://{bucket}.oss-cn-beijing.aliyuncs.com/x` 302 到 `http://100.100.100.200/latest/meta-data/`（阿里云 ECS 元数据，可窃取 instance-role 临时凭证）或任意内网 HTTP 服务，响应体原样回给攻击者。`http://` 协议也被接受。唯一缓解是 120/min 限流，而该限流 key 可被 XFF 伪造绕过（见 B4）。
- 修复：禁用重定向跟随（或每跳重新校验 scheme+host+解析 IP）；从白名单移除 aliyuncs.com（缩略图改走签名/CDN URL）；proxy 端点要求认证或按视频授权。

### B. 安全：高危集群的放大器与运维面

**B3. 限流 key 可伪造/坍缩（MEDIUM）** — nginx 只在 `/api/` 与 `/` 设置 `X-Forwarded-For`，`/media/` 原样透传客户端头；uvicorn 默认信任代理头。host 部署下攻击者轮换 XFF 即可绕开 /media/proxy 的 120/min（放大 A2）；容器网络拓扑下所有用户坍缩为 nginx 容器 IP，SMS 5/min 变成全站共享配额（可用性）。修复：`/media/` 补 `proxy_set_header X-Forwarded-For $remote_addr`，uvicorn 钉 `--forwarded-allow-ips`。

**B4. Redis 故障 = 全 API 500（MEDIUM）** — slowapi Limiter（core/limiter.py）无 fail-open 守卫（slowapi 0.1.9 存储异常直接 re-raise），Redis 抖动时所有限流端点（即全部 /api/v1）500；同期 SMS 冷却与 JWT 黑名单却 fail-open → 不一致的失效语义 + 短信轰炸窗口。修复：启用 `in_memory_fallback_enabled`/吞错降级；SMS 冷却改 fail-closed。

**B5. 草稿/未发布视频媒体公开可下载（MEDIUM）** — serve_media 无发布状态访问控制，finalize 转码即生成 `/media/{video_id}_720p.mp4`（UGC 尚在 draft 审核期），URL 可预测且无需认证。修复：/media/{video_id}* 接入与 shadowing 同类的授权门（capability token 或认证流式端点）。

**B6. LLM 成本放大 + 行为事件表无界写入（MEDIUM）** — `/ai/word-lookup` 的 sentence 无长度上限直入 LLM prompt（Pro 用户 20 次/分放大账单）；`POST /behavior/events` 匿名可无限写入无界 payload。修复：字段加 max_length、行为事件加批量/大小上限、按用户 LLM token 计数。

**B7. 低危但应顺手处理** — 全量手机号明文 INFO 日志（PIPL 暴露，auth.py/sms_service.py 多处）；未认证 `/metrics` + `/health` 泄露环境与组件状态；转写回调 payload 无大小/条数上限（共享密钥为唯一闸门，建议轮换 + 每任务 token）。

### 4.3 安全（2H / 4M / 3L）

**优点**：SSRF 防护分层且全入口强制（域名白名单 + 全解析 IP 私网/回环封锁 + DNS-rebinding 双重解析）；SMS 生产 fail-closed（Dypnsapi 服务端生成/校验、dev-fake 1234 生产硬禁、60s 冷却 + 每路由限流）；JWT 生命周期干净（算法钉死、access/refresh 类型区分、jti 黑名单、改密 iat 失效、封禁用户拒绝、回调密钥常数时间比较）；admin 鉴权统一（每路由 get_admin_user、角色读 DB 不读 JWT）；零 shell=True、yt-dlp/ffmpeg 全 argv 列表 + `--` 分隔；媒体路径穿越防护（relative_to）；密钥零提交（git ls-files 仅 *.example；.env*/cookies/media 全部 gitignore；GPU worker 启动守卫拒绝 DATABASE_URL/OSS_*）。

**发现**：A1/A2/B3/B4/B5/B6/B7 见 §3。补充细节：
- 上传大小检查在 `await file.read()` **之后**（整个文件先读进内存再校验）——大文件即内存 DoS，建议流式或先读头部。
- `/media/proxy` 的 Referer 伪造、5MB 上限、超时等防护存在，但重定向是主缺口。
- 转写回调 X-Callback-Secret 是全局共享密钥且随 worker 环境分发，泄露即可写任意字幕/置任意视频 error；建议轮换 + 每任务 token + payload 上限。
