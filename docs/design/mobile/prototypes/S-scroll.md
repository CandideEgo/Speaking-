## 0. 结论

**拍板 = A「画面贴顶常驻」。** 滚过画框之后画面**不缩、不飞、不消失**：**画框自己**贴到壳顶常驻（`sticky top-0`；移动端左列 `display: contents` 不产生盒子，画框直接成为 grid item，包含块＝整个网格容器），`<video>` 节点不换父，所以内联 ↔ 常驻切换不丢播放进度；画面里给一个 44×44 的「别再跟了」出口（落点在返回键正下方，避开入画字幕），点了就落回常规流、回到原位重新武装。

一句话理由：**另外三条都要拿「画面内那句唯一的当前句」去换几行文稿——A2 把它整块送出画，B 把它切掉一半，C 让它归零；而常驻这条一个像素都不用换，代价只是屏高。**

被否的三条与各自的读数代价（§2 有逐项）：

| | 形态 | 一句话代价 |
|---|---|---|
| **A2** | 只留一条（56px 标题条） | 入画字幕**与点词热区整体出画**：`wordTap 0/11`、`frame` 与 `burn` 的矩形均为 `0×0`（`display:none`）——#27「点词只在画面内那句上可用」滚动之后没有锚点 |
| **B** | 画面缩成条（定高 104px） | 长句被画框切掉：216 字符句在条内 `clientHeight 62` / `scrollHeight 107`，**只看得见 62/107px**，其余 `overflow:hidden` 永久不可达；标题两行也压进字幕（`tcTtl` 底 74.8 > `burn` 顶 66） |
| **C** | 右下角 160×90（现状） | 入画字幕份数归零（`burn display:none`，`wordTap 0/11`，INV-021 的锚点消失）+ 小窗压住文稿列表 90px + `fixed` 锚 layout viewport，地址栏一收放 `bottom` 差 **40px**（INV-019 的老账） |

## 1. 票面 6 问逐条回答

每条的「证据」栏只写实测读数与代码事实，不写推理。

### 问 1 · 播放器随滚动收缩成什么

**答：贴顶常驻，不收缩。** 粘滞元素是整块播放器块，`position: sticky; top: 0`（相对**滚动容器** `main#main-scroll` 的 scrollport，不是视口）。

| 证据 | 值 |
|---|---|
| 原型 A 档，滚到 600（滚动上限 8522） | `player` `position: sticky`、`top: 0px`；`frame` rect `375×210.9 @ (0, 64)`，`main` 顶边 = 64.0 → **画框顶 = 壳顶** |
| 同档在 0 / 100 / 300 / 600 / 727 / 1200 六个滚动位 | 画框顶恒为 **64.0**，`player` 恒 `sticky`（无自激振荡） |
| 三种「不是它」的形态 | top 粘滞条 = A2/B（§2）；右下角迷你窗 = C（现状，`page.tsx:1060-1069` 那段就是它留下的小窗退出键）；「滚出屏幕不再回来」= 无论文形态，`#30` 的票面原始三选一里它没有任何读数优势 |

> 票面第 1 问列的是三选一（顶部粘滞条 / 右下角迷你窗 / 直接滚出屏幕不再回来），原型只演示了前两条的四种落法；「滚出屏幕不再回来」没有单独的档位——它的代价是**每滚回来看一眼都要重新找位置**，与 #23「看+点词为主」直接冲突，故不进表、也不进复量范围。

**为什么是「整块」而不是把 `<video>` 单独粘住**：粘滞元素的 `sticky` 活动范围是它的**父盒子**。画框的父级只装播放器（app 里高度 ≈490px、`items-start` 下不拉伸），挂在那里只会跟着内层一起滚走（`page.tsx:923-929` 注释记的实测：滚 600px 时画框顶 y=**-232.8**，等于没粘）。

### 问 2 · 和 44px 常驻顶栏的关系：为什么不叠成 88px

**答：不叠，也不合并——顶栏**不让位**，两者直接叠成 275px 常驻。** 88px 这个数字的前提是「画面也缩」，而那正是 A2 与 B。

| 问法 | 实测 | 差的 12px 在哪 |
|---|---|---|
| 「合并成一个」的真实数字 | **100px** = 44（顶栏）+ 56（标题条；A2 档 `player` rect 高 56.0，落在 y64→120） | 那条 3px 细进度（#28 乙的常驻件）与「标题要两行才装得下」（`.tb-ttl` 一行放不下 44 字标题） |
| 「顶栏让位」的真实数字 | B 档：顶栏 64→44（`--topbar-h`），播放器块整块缩成 `max-height 132px / frame 104px` | 让出的 20px 从画面里扣，所以它和「画面不缩」互斥 |
| **A 档（拍板）** | **275px** = 64（顶栏）+ 210.9（画框）→ 取整 275；`listVisible 429`（滚到 600 时文稿列表可视净高） | 零——画面一个像素没动 |

**账要这样读**：275px 是「画面 + 顶栏」的合计，不是「白扔的常驻件」。A 档用 275px 换回来的是 `visiblePicture 133px`（画面净高，画框顶 → 入画字幕上沿）与 `wordTap 11/11`；A2 只用 120px（`permanent 120`）就把 `visiblePicture` 与 `wordTap` 一起变成 0。**省下的 155px 买的是文稿列表，花掉的是画面内那句唯一当前句。**

### 问 3 · 与底部导航的关系：为什么不压底栏（对齐 INV-019）

**答：常驻层与底栏在几何上不可能相交，而且没有引入第二个贴底 `fixed`。**

| 证据 | 值 |
|---|---|
| 原型四态 `fixedBottom`（`position:fixed` 且 `bottom < 200px` 的常驻件计数） | A / A2 / B = **0**；C = **1**（就是那个 160×90 小窗自己） |
| A 档画框下沿 vs 底栏上沿 | 画框底 274.9；原型壳 812 − 底栏 56 = 底栏上沿 **756** → 余量 481px |
| app 侧同一条断言 | `mobile-pip-scroll.spec.ts:200-230`：`frame.y + frame.height ≤ tabBar.y + 1`，且 `probe.fixedBottom` 必须 `[]` |
| 底栏本身 | INV-019：`MobileTabBar` 是壳的**最后一行 in-flow**，永不 `fixed`；安全区是壳的事（`MainLayoutInner` 的 `env()` padding），底栏不得自带第二份 |

**sticky 不会悬空压列表**：`sticky` 的活动范围是它的**包含块**，而这里有一条实测出来的硬约束 —— **包含块必须比滚动范围留出余量**。原型里 `.player` 是 `.main` 的直接子元素，包含块＝整页内容，余量足够；app 里若把 sticky 挂在 490px 高的左列 grid item 上，包含块余量只有 635px < 滚动上限 707px：页面最后 ~72px 画面会被包含块底边推着走（实测滚到上限画框顶 y=**−28**、壳顶 64），而且把字幕卡/行动行/来源卡一起钉住 490px、703px 可视高只剩 189px 给文稿、列的透明缝隙还透出下面滑过的文稿。**落地因此与本文档第一版不同**：移动端左列是 `display: contents`（不产生盒子），被粘的是**画框自己**，包含块＝整个网格容器（余量 ≈900px），滚动全程画框顶恒 = 64 —— 回归见 `frontend/e2e/mobile-pip-scroll.spec.ts` 的 ①′（滚到滚动上限仍贴壳顶）。

### 问 4 · 收缩时机与动画

**答：判据不是「滚过画框下沿」，也不是「滚过字幕区」，而是「这一列的**自然落点**越过了滚动容器的顶边」。** 实现是**零高度哨兵**，不是被粘住的那个元素自己。

- 实现：`useStickyPip.ts:62-75` —— 往滚动容器第一个子元素之前插一个 `height:0` 的 `<div>`，每帧（rAF 合并）比一次 `sentinel.getBoundingClientRect().top < scroller.getBoundingClientRect().top - 0.5`。
- **为什么不能用被粘住的元素自己量**（这是本题唯一咬人的地方）：元素一旦 `sticky`，它的 `getBoundingClientRect().top` 就恒等于**钉住的那个位置**（注释记的实测 64.0），「顶边被推上去了吗」永远问不出答案 → 测一次、置位、下一次测量立刻判回 `false`，class 一撤元素弹回原位、又被判 `true` → **sticky/static 自激振荡**（注释记的实测：滚到 100 / 300 / 727 时 `colPosition` 在两者之间翻，画框顶在 **64 与 -36** 之间跳）。
- **为什么不用 `IntersectionObserver`**：一次跳转滚动（在文稿列表里点一句直接跳下去）会让状态从 `false` 保持 `false`，观察器根本不回调，常驻便永不触发。
- **为什么监听要捕获阶段**：滚动容器是壳里的 `main#main-scroll`（`flex-1 overflow-y-auto`），`scroll` 不冒泡且 `window.scrollY` 恒 0（INV-022 已记）→ `window.addEventListener("scroll", schedule, true)`（`useStickyPip.ts:86`）。
- **判据变了这件事本身**：旧判据是「画框真的跑出视口顶部（`bottom ≤ 0`）」，那对应的是**缩成右下角小窗**那一态（元素脱离文档流、飞到底角）；改成贴顶常驻之后这个元素永不滚出视口，判据必须换成「顶边被推上去了」（`useStickyPip.ts:33-35`）。INV-023 记的仍是旧口径，本票不改那个文件，交由知识层维护者收口。

**「动画」= 没有动画，也不需要动画。** 常驻前后画框 rect 逐像素相同（`375×210.9`，顶边恒 64.0），所以切换只是一次 `class` 的加/减：不跨帧、不重排画面、不需要过渡曲线。原型四态共用同一份 DOM、切换只改 `data-mode`/`data-bar`（`S-scroll.html:286-293`），量的就是「不重建节点」这个实现。

**在原型上量这件事要按滚动数学读**（供复跑者对齐）：

| 档位 | `player` 的 `top` | 画框顶（实测） | 哨兵判据从哪个滚动位起为真 | 原因 |
|---|---|---|---|---|
| A（拍板） | `0` | **恒 64.0**（常量：`main.top + 0`；在 0/100/300/600/727/1200 六个位都量到 64.0） | **1px**（`sentinelTop` 64→63 一越过 `scrollerTop − 0.5` 即为真，此后恒真；0 时为假） | 列的自然落点本来就与夹取位相等（列首那记 `-mt-6` 出血让画框顶 = 壳顶），所以「开始跟人」在这条形态下**不可见**、也不该被当成动画时机。画框顶恒为常量也说明：`frame.y` **量不出**这一档的状态，判据只能来自哨兵或 computed `position` |
| B | `-20px` | 0 时 **44.0** → 100 起 **24.0** | 同款哨兵 | 顶栏让位到 44px，粘滞块要往上 20px 才落在顶栏下沿（`44 − 64`）；B 的 `top` 写成 `0` 会多留 20px 缝 |

### 问 5 · 入画字幕跟着画面一起缩吗

**答：不缩、不出画、不退回伴侣条——它原地不动，因为画面原地不动。** 详见 §3。

### 问 6 · 地址栏收放要不要重算

**答：常驻这条路**天然免疫**；只有被否的 C 要重算，而它的账是 40px。** 详见 §6 与 §2-C。

- A 档在地址栏收放模拟下（原型按 `v` 键把 `--vvshrink` 置 40px）：画框顶仍 64.0、`player` 仍 `sticky`，读数与未收放时逐项相同——因为 `sticky` 锚的是**滚动容器的 scrollport**，壳高变化由 `dvh` 那一层（INV-020）吸收。
- C 档同一开关：`player` 的 computed `bottom` 从 **68px → 108px**（+40），即窗口底边相对 layout viewport 多让出 40px。`fixed` 锚的是 **layout viewport（= `100lvh`）**，地址栏展开时可视区只剩 `100dvh`（−40px）→ 这个窗口的落点比可视区底边低一截，正好落在底栏/地址栏那条带上。这就是 INV-019 记过的同一笔账（真机实测：45px 的标签压住地址栏上沿）。

## 3. 入画字幕与点词的去向（票面第 5 问）

**结论：字幕不跟着缩，也不退回伴侣条，更不消失——因为画面没缩，它原地不动。**

| 口径 | 要求 | A 档实测 |
|---|---|---|
| **INV-021**（当前句全页只渲染一次） | 同一句渲染两遍会让点词热区分裂，词卡落位失去唯一锚点 | `burnCount = 1`（四态皆为 1；A/A2/B/C 都没有复制第二份） |
| **INV-022**（浮层锚点） | 词卡顶边 = 画框下沿、跟读抽屉底边 = 底栏上沿；两者都不许改变播放器几何 | 画框常驻时仍 `375×210.9 @ y=64`，与首屏逐像素相同 → 词卡/抽屉的锚点算出来的数不变（浮层自身不在本票范围） |

**C 档的 `burnCount` 仍是 1，但那份字幕 `display:none`** —— 所以 INV-021 的断言在 C 档下**通过而无效**（计数只看 DOM，看不见的节点也算一个）。这条要写进判据解读：`burnCount === 1` 是**必要条件**，不是「字幕可用」的充分条件；`mobile-pip-scroll.spec.ts:228-229` 因此把 `burnCount` 与 `burnWords > 0` 成对断言，`burnWords` 只数得到真在画面里的那些词。

## 4. 与 44px 常驻顶栏的关系（票面第 2 问）

见 §1 问 2 的读数表。补三件只有从代码才能看出来的事：

1. **顶栏里那条进度已经存在**（原型 `.tb-prog`，`S-scroll.html:154-155`、`:201`）：A2/B 两档把它当作「合并成一条」的那一半。A 档不用它，因为没有「合并」这回事。
2. **`top: 0` 是相对滚动容器的 scrollport，不是视口**（`S-scroll.html:80-84`）：壳的顶栏在滚动容器之外，所以 `0` 就等于「顶栏下沿」。这里若写 `var(--topbar-h)` 会多让出 64px——原型的注释明确记了「write 一次量错过」。这条同样是 app 侧 `sticky top-0` / `sticky top-6` 那记负外边距账的同源问题（`page.tsx:923-934`）。
3. **app 侧实测过的两个错法**（`page.tsx:926-929` 注释）：① 挂在画框那一层 → 滚 600px 时画框顶 **y=-232.8**（等于没粘）；② 不补 `-mt-6` 的账 → 贴顶那一态画框顶落在 **y=40**、被 64px 的 TopBar 盖住前 24px（注释记的是「实测 40.0 vs 壳顶 64.0」）。两条都是**来源 = app 侧注释**的读数，本节以外的表不混用。

## 5. 与底栏的关系（票面第 3 问）

见 §1 问 3。要补的两条：

- **A 档的 275px 常驻不会与底栏争地方**：常驻是**壳的一部分**（列顶那一层），底栏是壳的最后一行 in-flow；`sticky` 被父列底边接管后整块跟着列走，不存在「悬空压住列表」这种状态。
- **小窗退出键的 44×44 是 A 档的硬要求**：旧的角落小窗关闭按钮实测 **24×24**（来源：`mobile-pip-scroll.spec.ts:186` 的注释「旧小窗实测 24px」，与 49 票基线里 INV-019 点名的「迷你播放器」同病），而 A 档的出口是左下角 44×44（`page.tsx:1060-1069`，`aria-label="关闭小窗播放"` 原样保留，成对 e2e 继续认它）。落点在**左下角**而不是右上角：右上角被 `ExamLevelSelector` 的收起药丸占着（同为 `z-20`，叠上去实测点不中），右下角是控制条与细进度的位置。

### 已知读数陷阱（复跑者必读）

1. **`fixed` 元素的 rect 在移动端仿真下不可信**：本仓 Playwright 的 `isMobile:true` 上下文里，C 档小窗的 `getBoundingClientRect()` 报 `[199, 0, 160, 90]`，而同一时刻的截图里它并不在 y=0（截图实测：小窗在画面顶部、压在顶栏上）。**几何只认 `getComputedStyle().bottom`**（实测 68px，= 底栏 56 + 12），这也是原型量尺把 `fixedBottom` 按 computed `bottom` 数、而不是按 rect 数的原因（`S-scroll.html:494-501`）。
2. **`pinned` 读数要等布局落定**：`main.scrollTop = N` 之后同步读会拿到**上一帧**的 rect（`sticky` 的夹取要等一次布局）。复跑脚本必须在每个滚动位之后过两帧 rAF（或 `waitForTimeout`）再读，否则会得到「A 档滚到 1200 却 `pinned:false`」这种假读数——第一版复量脚本就是这么错的。
3. **原型的 `pinned` 与实现的哨兵不是同一条判据。** 原型内部用「画框 `bottom ≤` 滚动容器顶边」（`S-scroll.html:338-345`）只为 C 档的小窗出场门控；常驻形态（`sticky`）下画框永不出顶边，所以这个布尔在本票的 A/A2/B 三档里已经**不表示任何东西**（实测在滚到 1200 时它仍是 `false`）。要看「有没有在跟人」就自己插哨兵（§7）或读 computed `position`。

## 6. 收缩时机与动画（票面第 4 问）

见 §1 问 4。一句话：**判据 = 零高度哨兵越过滚动容器顶边**（`useStickyPip.ts:62-75`），不是「滚过画框下沿」，也不是「滚过字幕区」。

为什么不是那两个直觉选项：

- **「滚过画框下沿就收」**：那正是旧判据（`bottom ≤ 0`）对应的形态——元素脱离文档流飞到底角。常驻形态下画框永不滚出视口，这条判据恒为假。
- **「滚过字幕区才收」**：字幕区（入画字幕）贴在画框**内部**下沿，它滚出视口时画框早已滚出视口 —— 判据会比需要的晚整整一个画框高（210.9px），中间那一整段画面已经不可见却不跟人。

还有一条只有量过才知道的事：**A 档下这条判据「永远为真」**——实测哨兵在 `scrollTop` 从 0 变 1 的那一刻就越过了顶边（`sentinelTop` 64→63 vs `scrollerTop` 64），此后一直是真。原因是列的自然落点本来就与夹取位相等（画框顶 = 壳顶），所以这一档不存在「跟/不跟」的可见过渡：画面从首屏起就在它该在的位置，滚动只让下面的列表动。**这不是判据失效，而是这档形态的必然结果**；A2/B 两档同理（它们的粘滞块也从一开始就贴在夹取位）。判据真正在做事的场合是 **C 档与「回原位重新武装」**：画面滚出滚动容器顶边 → 状态翻转；滚回原位 → `setDismissed(false)` 重新武装（`useStickyPip.ts:74`）。

**B 档的顶栏让位是「滚过之后」的事**（顺带记一条会让读数对不上的细节）：B 档在 `scrollTop 0` 时 `--topbar-h` 仍是 64（`player` 顶 44.0、44px），滚过 0 之后才切到 `compact` 的 44（`player` 顶 24.0），此后恒定。所以 §2 表里 B 的「顶栏已让位到 44」指的是收缩态（滚 600），首屏那一档顶栏还是 64。

## 8. 与票面/注释不一致的地方（复量出来的，照实报）

1. **`47/161px` 这个数复量不出来。** 唯一出处是 `mobile-pip-scroll.spec.ts:9` 的头部注释：「B「画面缩成条」—— 长句被画框切掉（216 字符句：条内只看得见 47/161px）」。原型 B 档实测：216 字符句（38 词）字幕块 `clientHeight **62** / scrollHeight **107**`，即**只看得见 62/107px**；同档 `visiblePicture` 是 **42px**（画框顶 → 字幕上沿），短句时 `visiblePicture` 是 **47px**。161 与我量到的任何一档都对不上（16px 字号下，能凑出 161px 的句子长度在 300 字符以上；实测 301 字符句是 `62/125`，179 字符句是 `62/89`）。**结论不变**（B 档确实切掉长句，而且 216 字符句只看得见 62/107px），但引用到的具体数字要按本节改；那个 161 疑似是「未截断时的整块高」按另一档字号估的，复跑时若拿到 161 请把句子的真实字符数一并记下。
2. **`burnClip = 0` 会骗人。** 原型量尺把「字幕被画框切掉多少」算成 `frame.top − burn.top`（`S-scroll.html:466-467`），B 档下这个数恒为 0——因为 `burn` 自己就被 `max-height:62px` 截断了，超出部分不在它的矩形里。B 档的截断必须用 `scrollHeight` vs `clientHeight` 量，不能用 `burnClip`。
3. **`page.tsx` 注释里的 `490px` 与 `-232.8` / `40.0 vs 64.0` 都是 app 侧读数**（错法① 挂错层、错法② 不补 `-mt-6` 的账），本文件的四态表里一律没用它们；引用处已逐条标注来源。
4. **`burnCount = 1` 在 C 档是「通过而无效」**：C 档那份字幕 `display:none`，DOM 计数仍是 1（§3）。INV-021 的断言要与「字样在不在画面里」成对读。
5. **顶栏 44px 是原型按档位量出来的，不是 app 的现状读数**：原型里 `.app[data-bar="compact"] { --topbar-h: 44px }`（`S-scroll.html:20`）只在 B 档（且滚过 0 之后）生效；app 侧 A 档走的仍是 `MainLayoutInner` 的 64px 顶栏（INV-024 口径）。§1 问 2 的 275 / 120 / 148 都是**原型读数**（275 = 64 + 210.9 的那个 64 来自原型实测的顶栏高，不是 app 的推测）。
