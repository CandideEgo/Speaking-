移动端播放页 —— 三个变体

同一份数据、同一套外壳脚本、同一个点词容器，只变布局。三个都按 375×812 设计并按这个尺寸量过。 右上角「屏高构成」按钮会把该变体自己申报的屏高分配摊开——数字与该变体真实元素边界对齐，误差 ≤3px。 点英文单词可唤出底部词卡。

先把口径统一：三个变体的 16:9 画面几乎一样高

点词怎么点？本页三个变体共用同一个点词容器（底部弹层）。这个容器连同「点词触发」本身在 #27 · 点词的触发与呈现（三条路线） 里另做了一轮原型 —— 甲乙丙选定后再回头改这里。
跟读这块住哪？本页三个变体都把跟读当成字幕卡里的一行操作。它展开后的容器（行内 / 抽屉 / 整页模式） 连同「录制中的状态、退出、自动推进」在 #26 · 跟读与练习区的容置（四条方案） 里另做了一轮原型 —— 外壳沿用这里的乙。
字幕条为什么这么高、画面为什么这么小？乙 把字幕烧进了画面，于是可见画面只剩 67px、画面下还有 437px 的文稿列表。 字幕占几行、字号档位、画面内谁给谁让位、整段文稿摆哪 —— 这四问在 #28 · 入画字幕的版式与整段文稿的入口（四条路线） 里各走了一条极端（每条只改一个变量）。

这是整件事最反直觉的一点——它们不比谁的视频大。差别在于：屏幕上下被外壳吃掉多少、 画面里有多少是永久被别的信息占掉的、以及字幕区拿到多少。

三者共有（刻意固定，不参与比较）

演示数据 _demo.js、外壳与标尺 shell.js、基底 _base.css、词卡容器（底部弹层）—— 三个变体完全一致，所以横向差异只可能来自布局本身。
没有联网请求：不用 Tailwind CDN、不用外部字体、不用外链图片，断网也能开。
怎么打开：本页用 iframe 内嵌三个变体，file:// 直开时 Safari 会拦掉本地 iframe（Chrome 不拦）。 被拦了就点每个卡片下的「单独打开 →」，或在 docs/design/mobile/prototypes/ 下起一个静态服务： python -m http.server 8099，然后开 http://127.0.0.1:8099/。 懒得开浏览器就看静态截图：shots/A.png · shots/B.png · shots/C.png（375×812 @2x）。

怎么选

  1. 顶部那 20% 的留白，值不值得拿导航换？甲把它砍到 0，但代价是播放页上再也没有底栏——从播放页去「词汇」得先退出。
  2. 字幕入画，换来的视线折返值不值那 37% 的画面？乙的画面只剩 132px 高（211 里被字幕挖掉 79）。
  3. 丙的修补够不够用？如果够，就不必动外壳，风险最小；如果不够，甲乙里挑一个。
  4. 三方共同的一条天花板：行内点词做不出 44px 热区——22px 行距就是天花板，外扩到 30px 已经会与相邻行重叠。要让点词真正好按，得改交互形式，而不是改尺寸。

已知的不足（别当成设计结论）

静态原型证明不了真机行为：地址栏收放时 h-screen 的表现、安全区、以及滚动中的迷你播放器 都只能靠真机看。甲里的迷你播放器是固定示意的静态小窗，不是真的滚动触发。 这些归 docs/design/mobile/ 的「真机现状基线」那张票。
