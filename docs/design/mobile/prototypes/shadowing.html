#26 跟读与练习区的容置 —— 四条方案

页面重心已经定了：看 + 点词为主，跟读降级为按需展开的次要操作（#23）。于是这一票要回答的是 ——跟读这一整块（逐句跟读 + 录音 → 实时波形 / 对比波形 / 跟读历史）在移动端住哪、怎么展开、怎么收起。 本页是同一份数据、同一套外壳（#24 乙：细顶栏 + 入画字幕 + 字幕条 + 文稿列表）上的四条容置方案， 全部按 375×812 设计并按这个尺寸量过（Playwright，取 getBoundingClientRect()）。

硬约束（先立在这）：展开态不能挤掉播放器。 四条方案都做到了 播放器高度 211px 一动不动 —— 差别不在「动不动播放器」，而在 为此让谁让位：甲挤文稿列表、乙盖文稿列表、丙换掉整页（画面缩成 160×90 停靠条）。
口径先说清：P0 不是今天的整页。 今天播放页没有伴侣条、没有入画字幕（那是 #24 才引入的）。为了能横向比，P0 把 「今天的展开态原样」塞进了 #24 乙 的外壳里——mic 行、AudioWaveform 的 200px 画布、 WaveformCompare 的 400px 画布、Button size="sm" 的 30px 按钮、hover 才出现的删除键， 尺寸一个值都没美化。所以 P0 的作用是「可量的参照」，不是「今天的截图」。

怎么读数

每个原型左下角有个 「量给我看」 按钮：点开后会按真实的 getBoundingClientRect() 把 播放器有没有动、容器占多少、谁被盖/被挤多少、最小触控目标、波形实宽 一条条列出来，并在界面上画出虚线框。
右上角黑面板是可切开关 —— 这些就是第 ③④⑤ 问的全部内容，别用文字答，直接切给我看：
· 四案共有：波形合并 / 两条分开、自动推进 开/关、跟读时视频 暂停/继续放；
· 甲/乙：最近跟读 全展开/折叠一行、入口 画面角落/伴侣条原位；乙多一个 抽屉高度 半屏/抬到画面下沿；
· 丙：画面 保持 375×211 / 缩成 160×90、练习层里的原句 去掉/保留。
状态机是自动跑的：点「开始跟读」→ 放本句 1.6s → 自动开录（计时开始）→ 停止 → 回放对比。

三案的波形位宽都是 291px —— 差别不在「谁的波形宽」，而在容器给内容多少实宽。三案的最小触控目标都是 44px， 这一条是四案里唯一由「方案」而非「容器」决定的：把 AudioWaveform 的 200px 画布与 WaveformCompare 的 400px 画布 换成「按容器实宽画」，30px / 24px 的问题就一起消失了。

现状的尺寸问题（真代码位置，动手前先看这几行）

  • 回放态撑破容器 197px：WaveformCompare.tsx:125-127 的 <canvas width={400} height={28} className="flex-1"/> 内在 400px，放进 303px 的口袋里 —— 实测「行要 488px vs 容器 303px」。文案 波形仅供对比参考，不做评分 也在同一行（WaveformCompare.tsx:234），是最难看的那个标签。
  • 录音行撑破 2px：AudioWaveform.tsx:84 的 <canvas width={200} height={32} className="rounded-md"/> 没有任何宽度类，200px 是它的内在尺寸；listening 行的 flex-1 也没有 min-w-0，于是顶破那一格。
  • 触控目标 24px / 30px：删除键 ShadowingHistory.tsx 是 w-6 h-6 + opacity-0 group-hover:opacity-100 —— 触屏上根本摸不到（没有 hover）；动作行三个按钮是 Button size="sm"（Button.tsx:41 ≈30px 高）。
  • 计时没画出来：useSpeakingRecorder.ts 有 seconds，但注释说 timer「currently unused」； page.tsx:118 却传了 {timer:true} —— 自相矛盾，录音中不显示秒数。
  • e2e 从没跑到回放态：frontend/e2e/mobile-d1-d10.spec.ts:152-164 的波形断言只在 「波形仅供对比参考，不做评分」可见时执行，否则打印 [D10] waveform not visible… 跳过； 而该 spec 从不 mock getUserMedia，所以它永远走不到 reviewing 态 —— 这条断言等于没测。 上面这些问题（200/400px 写死、30/24px 目标）没有一条被测试拦住。

这五条不是「顺手改改」：它们都在 page.tsx:954-1169 这一段里，而这一段正是 #26 要重做的对象。 所以本票的结论一落地，这几行会被整段替换——列在这里是为了让「重做」有个明确的靶子，不是另开一张票。

四条路的取舍，其实就是四句话

  • 甲：用「练习期间文稿列表被挤」换「什么都不浮、退出零惊喜」。最像「从字幕条长出来」的一段，也最不需要新手势。
  • 乙：用「盖住文稿列表 + 一个下拉手势」换「容器够大、拇指够得着、历史能全展开」。半屏时中间那 166px 断层看得见。
  • 丙：用「整页被换掉 + 画面缩到 160×90（入画字幕没了）」换「跟读成一件事、进出明确、原句能放到 19px」。代价最大，收益也最整齐。
  • 共性：三案都顺手修掉了 200/400px 写死、30/24px 目标、无计时——这些与选哪个容器无关，是组件层该修的。
本页不替你决定。#26 是 HITL 票：五问里 ①②④ 选一个容器基本就全定了，③⑤ 是组件与默认值层面的事。 挑一条（或各取一块，例如「甲的『不浮』口径 + 丙的『整层』骨架」），把结论写在 #26 里。 真机手感（抽屉的跟随、地址栏收放、安全区、长按的可达性）这一页证明不了，归 #22。 另外：#27（点词）的裁决若选了「词不在画面内点」，画面内字幕的前提会变，届时 #28（入画字幕版式）要重切 —— 与本票的容器读数无关，但会改外壳。

已知的不足（别当成设计结论）

· 不真录音、不碰麦克风：原型不调 getUserMedia，波形是按 seed 画的确定性包络，<audio> 的 src 是一段 0.4s 静音 WAV（好让原生控件真的画出来）。
· 数据是演示数据：5 条「最近跟读」写死在 _practice.js，不是真实 attempts。
· 状态机是简化的：复刻了「放本句 → 句末自动开录 → 停止 → reviewing → 下一句」的顺序，但没有真实音频的时长/失败分支。
· 静态原型证明不了真机行为：抽屉的橡皮筋、下拉手势的阈值手感、地址栏收放时的 h-screen、安全区 —— 都归 #22。
