# 真实字幕压力测试（wayfinder #28）

把**生产服务器上的真实字幕**灌进 甲（`B1-fit.html`）与 乙（`B2-tap.html`），在 375×812 @2x 下量「可见画面」。

## 为什么要做

原型自带的演示语料（`../_demo.js` 那 10 句 "discipline"）与本地库里的
`E2E Demo Video (CI seed)` **逐字相同**，长度 33–70 字符（中位 54）。
生产字幕不是这个量级：

| 语料 | n | 中位 | p90 | 最长 |
|---|---|---|---|---|
| 原型演示语料（CI 种子） | 10 | 54 | 70 | 70 |
| 生产库采样 | 279 | 78 | 118 | 236 |
| 生产库采样（另一批，本目录用） | 131 | 88 | 129 | 216 |

**原型语料的最长句，够不着生产字幕的中位数**（70 < 78）。**62.7% 的生产句超过 70 字符。**
用原型自己那份语料做版式决策，会把问题低估一倍。

## 数据从哪来

- **`corpus.js` → `five`**：截图那条 CNBC《How Micron's Building Biggest U.S. Chip Fab》里可见的 5 句，
  中英对照齐全（视频 `63288cd3-2789-47d7-ba66-a83c982f33a9`，C1，17:43）。
  长度 32 / 131 / **179** / 131 / 82 字符。
- **`corpus.js` → `sampled`**：从生产库的公开字幕搜索端点
  `GET https://seeword.top/api/v1/videos/search/subtitles?q=` 采样去重得到 131 句（仅英文——该端点不返回中文）。
  查询词：`the / memory / company / people / think / about / because / really`，每次间隔 4.2s 避开限流。

**已知偏差**：搜索采样偏向含这些常见词的句子（对长度分布基本无偏），但索引里混有少量逐字稿碎片
（如 `"Jey, I understand - Her ribs were busted by the"`），所以短句那一端可能被高估。
全片精确分布需要从库里按 `video_id` 直接取——本机 SSH 到生产不通（22 端口超时），API 对匿名不返回字幕（登录墙）。

## 怎么复跑

```bash
node docs/design/mobile/prototypes/_real/run.js
```

它**不把原型复制进仓库**：每次从当前原型目录在系统临时目录里拼一份 fixture，
只把 `_demo.js` 换成真实语料，量完即删。原型永远只有一份真身，快照不会烂掉。
产物是 `shots/` 里的截图 + 控制台里那三张表。

## 三个读数

### 一、5 句真实字幕（中档 16px）

| 句 | 字符 | 甲·仅英文 | 甲·中英双语 | 乙·中英双语 |
|---|---|---|---|---|
| And this is the first major one. | 32 | 1 行 · 108px | 1+1 行 · 89px | 1+1 行 · **151px** |
| For now, Micron is still in China… | 131 | 3 行 · 64px | 3+2 行 · 28px | 3+2 行 · **90px** |
| That's possible because memory… | 179 | 5 行 · 20px | 5+2 行 · **−16px ⚠ 顶出画框** | 5+2 行 · **46px** |
| What I'm going to find really… | 131 | 4 行 · 42px | 4+2 行 · 6px | 4+2 行 · **68px** |
| you might see China diving back… | 82 | 2 行 · 86px | 2+2 行 · 50px | 2+2 行 · **112px** |

**同口径对打：乙 每一句都比 甲 多 26px（短句多 43px），同时画面里还多一整套中文。**

### 三、131 句生产字幕的分布（仅英文 · 中档 16px）

| | 中位 | 最差 | 跌破 #24 基线 67px | 折行分布 | 实际生效字号 |
|---|---|---|---|---|---|
| 甲 · 允许长高 | 86px | 20px | **40%** | 1行16 / 2行62 / 3行43 / 4行6 / 5行4 | 16px × 131（全部） |
| 甲 · 降档封顶 | 92px | 35px | 6% | 1行23 / 2行90 / 3行10 / 4行6 / 5行2 | **14px × 113（86%）** · 16px × 18 |

甲长高与乙的折行分布**完全一样**——那 62px 的差 **100% 来自控制条**，与语言、字号、内容无关。

## 结论

1. **同口径（同语言、同字号、同内容）下，乙 每一句都比 甲 多 62px**，并因此把「画面会不会被字幕吃掉」这件事从「40% 的句子会」变成「一句都不会」。
2. **甲 的算术是反的**：它让掉中文，省下的是中文那一行——**随句子浮动**，本批里 19px（1+1 行句）
   到 36px（5+2 行句）；而它为此付出的常驻控制条是**固定 62px**。
   固定成本比它能省下的最大值还大。乙 双语（中位 148px）比 甲 仅英文（中位 86px）多 62px，**还多给一整套中文**。
3. **甲 独有的失败模式**：中英双语档下，长句会让字幕块**顶出画框**（179 字符 → 溢出 16px，200px 块 → 溢出 54px）。
   画框是 `overflow:hidden`，所以溢出的部分是被**切掉**的——首行英文上半截没了。
   甲 的默认档是「仅英文」（不溢出），但用户用 Aa 切回双语就会碰上。
4. **甲的「2 行封顶」在真实内容上不存在**：允许长高时 40% 的句子 ≥3 行（10+6+2＝18 句，14% 仍有 3 行以上）；
   而且降档封顶为此把 **86%** 的句子降到最小档 14px（113/131），换来的是中位 86→92px——**+6px**。
   也就是：它把九成的正文调小，只买回来 6px 画面，而且仍封不住那 14%。
5. 像素账本回答不了的问题：「中文该不该待在画面里」是教学决定，不是版式决定。

## 纪律

量尺只读，不改被测对象；读数是真实的 `getBoundingClientRect()`；
每张截图上的「画框标注」都跟同一态的实读对过账（乙 的标注曾写死 `375×129`，2026-09-30 接上量尺）。
