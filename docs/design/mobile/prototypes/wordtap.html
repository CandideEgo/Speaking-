#27 点词的触发与呈现 —— 三条路线

乙（#24 选定）把字幕搬进了画面，点词因此断成两截：热区在画面上部、词卡从屏幕底部升起，中间隔 470px。 本页是同一份数据、同一套外壳（topBar: compact + tabBar: visible + 乙 的入画字幕）上的三条点词路线， 加上 #24 的原样对照。三个都按 375×812 设计并按这个尺寸量过（Playwright，取 getBoundingClientRect()）。

硬约束（先立在这）：词卡不能遮住刚点的那句。 实测结论：三条路线都做得到 0px 遮挡 —— 甲让句子和词卡同处一个不滚动的停靠区、乙把卡口抬在字幕下方、 丙把来源句钉在面板顶部。真正的差别不在「遮不遮」，而在为此让谁让位，以及触发那一下要付多少。 对照（底部弹层）也只是「够不到」而非「遮得住」——它遮的是文稿列表。

怎么读数

每个原型左下角有个 「量给我看」 按钮：点开后会按真实的 getBoundingClientRect() 把 词热区、卡与句的距离、谁被盖掉多少 一条条列出来，并在界面上画出虚线框（①②③④）。 右上角的「屏高构成」是 #24 留下的标尺，标的是空闲态的屏高分配 —— 三条路线的空闲态与乙 完全一致，所以共用一份。

两个可切开关（黑面板里）：点词后是否暂停、加入词库后是否自动关；乙 多一个 卡口（贴画面下沿／贴字幕下沿）。 这三个开关就是第 ③ 问的全部内容 —— 别用文字答，直接切给我看。

这条路线的取舍，其实就是三句话

  • 甲：用「多一次点击 + 字幕条让位 + 查词时文稿让位」换「44px 热区 + 焦点句永不消失 + 逐句翻」。
  • 乙：只解决「卡离得远」。它承认 22px 行距是天花板，于是把点词缩到只剩画面内那一句；文稿里想点词就得多一步跳句。
  • 丙：把点词做成一次明确的进出（长按 → 选词态 → 退出）。热区够大、遮挡不可能，代价是看片被模态打断，且引入第二个手势。
本页不替你决定。#27 是 HITL 票：要回答的是「触发形式 / 词卡从哪出 / 点完之后 / 与入画字幕抢位」这四问， 而它们互相咬合 —— 选了触发形式，容器基本就被决定了。挑一条（或从三条里各取一块，例如「乙 的卡口 + 甲 的 44px 焦点条」）， 把结论写在 #27 里。真机手感（长按的可达性、地址栏收放、安全区）这一页证明不了，归 #22。
