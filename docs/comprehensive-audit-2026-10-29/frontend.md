## 现存发现

### FE-01：无限列表翻页失败后，“重试”跳过失败页（建议 P2，已复现）

- **证据**：`frontend/src/hooks/usePaginatedList.ts:201-206` 在请求成功前递增 `page`；`frontend/src/components/home/HomeFeed.tsx:225-227` 的“加载更多失败，重试”继续调用 `loadMore`；`usePaginatedList.ts:165-171` 的 page effect 与 `:185-187` / `:203-205` 的直接请求会同时触发同页读取。
- **复现**：第 1 页成功，第 2 页失败，点击现有重试入口。实际结果 `page=3`，列表为第 1 页与第 3 页，第 2 页未恢复；hook 请求序列为 `1,2,2,3,3`。API 在途去重可能合并部分网络请求，因此不能把双重 hook 调用直接当作每次都发生两条 HTTP。
- **影响**：网络抖动后用户永久漏看该页，列表计数与内容不一致；共享 hook 的 append 消费者均应检查。
- **建议**：区分“最后成功页”和“当前请求页”；失败重试同一页；让 page effect 或显式请求成为单一触发点。
- **验收**：页 2 首次失败、重试成功后顺序为 1→2→3；每次翻页只触发一次 fetcher；连续筛选/返回/哨兵重入均无漏项和重复项。
- **置信度**：高，源码及执行复现；真实浏览器尚未复跑。

### FE-02：学习时长以播放位置差累计，拖动、循环与短会话导致指标失真（建议 P1，已复现）

- **证据**：`frontend/src/lib/analytics.ts:127-142` 每 10 秒用 `currentTime - wtLastPos` 生成 `delta_s`，没有逐段累计，也没有尾段结算；`frontend/src/app/(main)/watch/[id]/page.tsx:293-301` 从播放 tick 调用；`backend/app/services/behavior_service.py:140-156` 直接把该值累加到 `LearningRecord.time_spent_seconds`。
- **复现**：正常播放 10 秒计 10；10 秒时拖到 120 秒计 **60**；5 秒片段反复听 20 秒计 **0**；观看 9 秒后离开计 **0**。后两项正好损害逐句重听和碎片学习的核心场景。
- **影响**：个人进度、分钟目标与后台学习投入统计失真，后续留存/效果优化会用错数据。历史总时长未必能按现有数据完整修复。
- **建议**：先明确“实际有效学习秒数”与“媒体覆盖秒数”两种定义；基于 playing/paused/seeking/rate/visibility 的状态和单调时钟累计有效时长，暂停/切片/离页结算尾段；事件有稳定 id 并在服务端去重与约束增量。不要直接覆盖历史口径，应记录版本/生效日。
- **验收**：拖动不增加学习秒数；循环、0.5×/2×、暂停与后台切换按定义计时；9 秒离页保留尾段；重复投递不重复累计；用户进度与后台同口径。
- **置信度**：高，原模块执行复现；未量化生产受影响人数。

### FE-03：购买页没有解释内测全量免费与付费增量，会员到期文案与当前访问事实不一致（建议 P2 产品决策项）

- **证据**：`frontend/src/app/(main)/upgrade/page.tsx:35-55` 把点读、复习、词单真题、多端同步列作会员能力；`:273-275` 显示“会员能做什么”；`:433-434` 称到期后“不再解锁会员内容”。实际 `backend/app/services/unlock_service.py:65-77` 对所有登录用户返回 `unlocked=True`、不限量，忽略 plan。页面未解释当前内测免费范围/期限或本次购买的具体增量。
- **影响**：用户难以判断为何付款，以及现在付款将得到什么；客服与续费预期缺乏可验证承诺。这是产品与代码的契约差异，不证明已经发生投诉或违规。
- **建议**：产品先确定内测付费定位、当前权益、未来承诺与已购用户处理；把免费范围和可兑现的增量明确写到购买页及后台配置。若定位为支持开发，须直接表达该定位；是否暂停购买需负责人决定。保持当前免费访问规则，不能为了匹配文案擅自加付费墙。
- **验收**：免费、付费、过期三类账号的页面承诺可逐条与实际功能对照；购买前能看清金额/期限/当前增量/生效时点；管理员能追踪购买、确认与到账状态。
- **置信度**：代码/文案差异高；生产购买配置及真实用户认知本轮未验证。

### FE-04：无限期 Pro 的前后端有效性判定不同（建议 P2，静态确认）

- **证据**：`frontend/src/lib/api.ts:108-113` 将 `plan='pro', plan_expires_at=null` 判为 false；`backend/app/services/unlock_service.py:47-50` 将同值判为 true。后端函数的注释还声称两端镜像，实际并非如此。
- **影响**：存在这种账号时，服务端视为有效 Pro，购买页/前端标签却显示免费。当前内测不阻断视频，但商业状态与管理统计仍可能不一致。
- **建议**：明确 null 表示“永久有效”还是“数据缺失”，让 API 显式返回有效会员状态或从契约生成相同判断，迁移历史异常值前先统计消费者。
- **验收**：free、未来到期、已过期、null 到期、无时区数据有前后端契约测试；所有用户端与后台使用同一语义。
- **置信度**：判定差异高；生产是否存在该账号未查询，不将其写成已发生事故。

### FE-05：前端行为采集不能解释完整激活和学习闭环，性能优化也缺少当前基线（建议 P2，能力缺口）

- **证据**：全 `src` 检索 `analytics/track/trackClick`，调用主要为视频卡点击、观看 play/pause/seek/complete/watch_time 和 onboarding 的 `demo_video_missing`。`FeaturedVideoCard.tsx` 的精选入口没有对应点击埋点；登录/注册、引导各步、查词→收藏→复习→练习完成没有统一前端路径事件。部分完成动作在后端已有业务事件，不能说“完全没有埋点”。
- `package.json`、`src`、CI 与现有 E2E 未检出 Web Vitals/RUM、Lighthouse 或 bundle 预算接入。当前首页是客户端读取数据，编排有 8 秒超时回退（`src/app/(main)/page.tsx:20`），但本轮没有可用的生产页面耗时或包体积基线，无法据此判定页面慢。
- **建议**：围绕“首次完成一次有意义学习”和“次日再次完成学习”定义版本化事件；补入口 impression/click、引导完成、首次点词、首次入库、首次复习/听写提交的关联键；统一后端结果事件，减少重复上报。先采集实际 LCP/INP/CLS、API p50/p95、错误率、媒体首播耗时与设备分层，再决定性能项目。
- **验收**：专用账号能从一次入口曝光追溯到首次学习完成；关键事件有去重、缺失率与版本；建立两周基线，并据此为移动端核心页面设预算。目标值需由当前基线与业务要求共同确定。
- **置信度**：仓库接入缺口高；线上是否有仓库外统计工具未知。

### FE-06：视频页与播放器职责集中，重构应按风险拆分（建议 P2，维护性改进）

- **证据**：`src/app/(main)/watch/[id]/page.tsx` 1,750 行、`src/hooks/useVideoPlayer.ts` 1,072 行；页面同时承担字幕状态、点词/词卡、笔记、布局、剪辑入口、来源导航、播放控制和行为采集。`HomeLayoutEditor.tsx` 1,013 行，管理编排也有同类集中。
- **影响**：改变一个播放交互会同时触及桌面、手机、字幕、导航和统计，审查与回归成本较高。大文件本身不证明功能错误，也不构成改框架理由。
- **建议**：以 FE-02 的计时边界为首个可验证提取点，再提取播放状态机/生命周期、字幕与查词动作、笔记持久化；保留现有外部契约与 E2E。不要做一次性全站重写。
- **验收**：每个提取有清晰输入/输出和行为用例，四个浏览器项目的观看闭环与布局回归通过；不是以文件行数下降作为唯一完成标准。
- **置信度**：职责分布高；未做团队周期/变更失败率量化。

### FE-07：通用请求和刷新请求没有统一期限，临时网络失败会清除可恢复会话（建议 P2，静态确认）

- **证据**：`src/lib/createApiClient.ts:283-285` 仅使用调用方 signal，没有默认请求期限；`src/app/(main)/MainLayoutInner.tsx:60-87` 的 onboarding 门等待 `/users/me`，没有期限或用户重试入口。`src/stores/authStore.ts:263-282` 对刷新返回 5xx 或网络异常一律 logout；管理端刷新也需要同类核对。
- **影响**：请求挂起可能使壳层长期停在骨架屏；access token 刚过期时短暂断网可能使仍有效的 refresh token 被清除。这里只确认代码路径，未复现真实网络事故。
- **建议**：定义读取/提交/生成任务的超时策略；区分确定无效凭据（401/撤销）与临时不可用（网络/5xx）；提供可恢复的会话重试状态，避免把临时故障当作账号失效。对可能已到达服务端的写操作不盲目自动重发。
- **验收**：挂起请求在规定期限进入可恢复错误态；刷新 503 后网络恢复可以继续，刷新 401 则清会话；写请求超时保留用户输入且不产生重复副作用。
- **置信度**：静态路径高；生产频率未知，浏览器故障注入未执行。

### FE-08：本机默认生产构建无法完成，需要恢复可重复的发布前验证（建议 P1 验证阻塞项）

- **证据**：两次 `npm run build`（沙箱内、沙箱外）均 exit 1，Next 16.3.7 Turbopack 在 `src/app/user-ui.css` 的 PostCSS 转换阶段提示 `creating new process / node process exited before we could connect to it with exit code: 0`。原始日志如上。
- **对照结果**：同一源代码、依赖锁与 Node v22.20.0，在沙箱外执行官方 CLI `npm run build -- --webpack` **exit 0**，完成编译、类型检查、46/46 静态页生成和构建 trace。未修改配置、依赖或业务代码。
- **影响**：静态检查、单测和 webpack 对照虽通过，本轮不能声称默认生产构建通过，也不能据当前结果保证默认发布镜像构建成功。现有证据将范围缩小到本机 Turbopack 的 PostCSS/Node 子进程通信路径，尚不足以把根因归为用户样式语法或应用业务代码。
- **建议**：记录 Node/npm/OS/依赖锁版本，在与 CI/镜像一致的 Linux 构建环境重现；核对 PostCSS worker 启动与进程通信。可用官方 `--webpack` CLI 做对照诊断，但其成功不能替代默认构建门，也不应直接修改配置来掩盖默认失败。
- **验收**：默认 `npm run build` 在声明的本机与 CI 环境 exit 0，产出 standalone；随后通过 HTTPS nginx 的生产专项回归。不得仅凭 `tsc`、历史 BUILD_ID 或替代构建器结果算通过。
- **置信度**：本机默认构建失败高；根因及 CI/生产影响范围待进一步验证。

## 执行顺序

用户已明确优先目标是“学习体验与用户留存”，据此排序：

1. 先统一学习时长语义（FE-02），补齐有效学习与回访的可核验口径。
2. 修分页恢复（FE-01）和会话故障恢复（FE-07），减少“找不到内容/丢失会话”的中断；补有意义的状态/契约回归。
3. 建立学习闭环事件与性能基线（FE-05），恢复浏览器验证条件后完成上述体验矩阵，按首次学习完成与 D1/D7 回访验证效果。
4. FE-03 先纠正文案真实性，FE-04 统一状态契约；本轮不投入收费增长或设计新付费墙。
5. 依靠实际缺陷与改动频率逐段重构（FE-06）；每阶段以用户闭环、正确统计和可重复验收作为出口。
