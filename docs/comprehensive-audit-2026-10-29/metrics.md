# 指标、学习记录与效果验证专项

日期：2026-10-29。目的：支持用户已确认的“学习体验与用户留存”。没有访问生产行为数据，因此不推断真实留存率、学习效果或收入。

## 已确认的计量问题

学习计时的输入失真见 [FE-02](frontend.md)，个人本周时长将历史累计归到最近访问日见 [后端报告](backend.md)。二者是独立缺陷：只修聚合无法修好错误输入，只修输入也无法解决历史累计被错误切片。

### MET-01 / P1：后台历史活跃趋势基于可变的最后访问时间

证据：`backend/app/services/admin_service.py:198-215` 按 `LearningRecord.last_accessed_at` 分日统计去重用户；`backend/app/models/learning.py:13-16` 每个用户/视频只有一条记录，`:33`保存最后访问时间。

一个人昨天看过某视频，今天再次访问同一视频，记录的时间会移动；昨天的活跃人数可能随今天操作变小。该查询统计的是“用户视频记录最后被访问的日期”，不能作为历史DAU或留存。它也遗漏纯词汇/听写/真题学习。`User.last_active_at`同样只是最后活动时间，不能用来恢复完整每日历史。

受控SQLite聚合演示：唯一观看记录从昨天更新到今天后，同一GROUP BY查询的桶从 `{2026-10-28: 1}` 变成 `{2026-10-29: 1}`。完整 `_compute_admin_stats` 在SQLite下另有日期字符串/日期对象匹配差异，报告不把该SQLite响应当作生产Postgres响应。真实Postgres路径因一次性容器退出未完成，缺陷结论依据源码与聚合语义，未推断受影响人数。

复跑脚本：[reproduce-metrics.py](evidence/reproduce-metrics.py)，最终结果：[metrics-reproduction-final.txt](evidence/metrics-reproduction-final.txt)。

建议：按不可变学习事件/明确的每日事实表统计；先定义“有意义学习”而不是任何API访问。以用户本地日期算个人进度，以统一运营时区或UTC展示全站统计并标注；迟到事件、重复事件与时区变化有确定策略。旧数据能回填多少取决于现有事件，不从最后访问时间伪造历史。

验收：昨日学习并在今日重访不改变昨日人数；词汇/听写/真题按定义计入；一个用户同一天多视频只计一次；跨日/跨时区/迟到/重复事件均有回归。

### MET-02 / P2：展示为“转化漏斗”的实际是相互独立的累计人数

证据：`backend/app/services/admin_service.py:253-264` 分别统计全部用户、存在LearningRecord的人、存在Vocabulary的人、有效Pro人数；`frontend/src/app/(admin)/admin/(shell)/stats/page.tsx:465-480` 将它们展示为“Pro转化漏斗”。查询不要求同一注册cohort、时间窗口或步骤顺序；Pro还可能来自试用/人工授予。

内存库复现2个注册用户：1个观看者、0个收词者、另1个从未观看的有效试用Pro，接口返回 `{registered:2, watched:1, vocab_saved:0, pro:1}`。末级人数大于前一级合法出现，不能解释成逐步转化，也不能视为付费人数。

建议：短期将当前图明确称为“用户行为与权益分布”，避免误读；另建真实cohort分析，付费只认已确认且匹配账号的付款事实，排除试用/人工赠送。留存优先下可先下调付费漏斗工作量，优先完成激活与回访分析。

验收：种子数据包含跨cohort、跳步、试用、人工Pro与付款用户；累计分布与时序漏斗分别返回有解释的结果，不混用一个字段。

## 建议的指标字典（待实施，不冒充已有能力）

| 指标 | 建议定义 | 必要分层/约束 |
| --- | --- | --- |
| 主指标 | 每周有至少2个“有效学习日”的真实用户数；占比的分母固定为该周至少1个有效学习日的去重用户数，另保留绝对人数 | 去除管理员/内部测试；新注册与存量分层；阈值在基线期确认，不能事后调整以做高结果 |
| 首次激活 | 新注册cohort中，24小时内完成一次明确学习任务的用户占比 | 首次视频学习、词汇复习、听写、真题分路径，不能强迫所有人走同一功能 |
| D1/D7学习回访 | 注册日或首次激活日的cohort，在第1/7个本地日再次完成有效任务 | 明确选择注册/激活口径与分母；以入组时区固定日期边界，不随之后改时区回写cohort；成熟后再比较，不拿后来的用户补分母 |
| 闭环完成率 | 任务开始→播放/作答→查义/保存或提交→看结果，各路径定义独立终点 | 同一flow_id、内容与事件版本；同时报告完成数和失败/放弃位置 |
| 续学成功率 | 点续学后到达预期视频/原句并可播放，且未被迟到保存覆盖 | 显式锚点、失效内容、跨设备、媒体失败分别统计 |
| 复习回访 | 已收词且有到期词的用户，之后完成到期复习的比例 | 只对有资格的人计算；去重词与session；提醒开关作为分层而非强制开启 |
| 学习效果观察 | 同一词在延迟复测的正确率，或同难度题的再次表现 | 控制重复题记忆、难度与自选偏差；不能凭观看分钟或一次分数证明能力提升 |
| 体验护栏 | 保存失败、认证中断、媒体首播失败、错误率、API p95、移动端LCP/INP/CLS | 设备、网络、版本、来源分层；数据量小则展示样本量，不制造精确提升 |
| 内容质量与成本 | 字幕/翻译质量门通过率、人工纠错率、ready耗时p95、每分钟内容成本 | 按来源/GPU/模型版本；真实英语人工听校与合成媒体测试分开 |

“有效学习”应由产品和代码共同确定。例如有效播放、完成一轮复习、提交听写/试题可各有不同门槛；本轮不随意设定30秒、3词之类阈值后宣称代表学习效果。

## 采集与数据质量

现有 `BehaviorEvent`（播放/点击等）和 `LearningEvent`（结构化学习结果）应继续服务各自职责。给关键事件建立明确契约与版本，不新增第三套同义事件总线；以服务器提交成功为可靠结果，客户端意图只用于路径分析。

必要字段：event_id、schema_version、server_ts、client_ts、user_id/匿名标识的关联策略、session_id/flow_id、内容/题目来源、客户端发布版本；避免原始手机号、token、完整答案/笔记进入分析payload。已定义事件应有长度/枚举和传输上限，结果去重必须覆盖重试与离页投递。制定原始事件保留期、聚合与删除策略，再测数据量、索引和备份开销；当前没有足够证据指定分区或引入数据仓库。

在隔离账号上验证每条路径，核对客户端发起、服务端接收和最终业务事实的一致性，记录丢失率/重复率。计时修复与新口径设生效日期，不能把新旧曲线拼起来解释成增长；历史无法恢复的数据明确标为不可比。

## 研究与实验节奏

先邀请5–8名目标用户做形成性任务测试（人数是研究计划，不是统计充分性证明）：首次找内容并完成短学习；隔天续学；找到收下的词并复习；完成一次专项并查看结果。记录成功/耗时/求助/退出原因及原话，使用同意后的最小必要资料。

建立至少两周可用基线后，每次验证一项假设，如“回访入口可被找到”“首次任务下一步更明确”“复习结果能回到来源”。立项时写出目标人群、主指标、护栏、观察窗口与撤回条件；有足够样本时预先做A/B样本规划，小样本用任务成功率与定性证据，不能把自然周波动解释成因果。任何设计改动只有在数据质量和可靠性护栏未变差的情况下才扩大。
