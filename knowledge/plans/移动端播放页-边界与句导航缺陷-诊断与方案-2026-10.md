## 0. 一句话

「上一句」被 **Next dev 指示器**吞掉点击（只在 dev，这就是「开发环境差异」的真身）；「下一句」拿到的是**过期闭包**，会把当前句**往回跳**（生产同样存在）；「两个容器边界突兀」是**当前句卡与文稿面板两套容器语言零间隙相撞**（设计问题，任何环境都一样）。另外，这套 UI **一行都还没提交**，所以「生产看着不一样」的第三层原因是**版本差**，不是配置差。

## 2. 逐条证据

### 2.1 P0：「下一句」是过期闭包（实测复现）

代码：
- `frontend/src/app/(main)/watch/[id]/page.tsx:733` —— `onNext: handleNextSubtitle`；
- 同文件 `:639-653` —— `handleNextSubtitle` 是**每次渲染新建**的普通函数，闭包里读 `currentSubtitleIndex`；
- 同文件 `:739-751` —— memo 依赖表：`video, selectedExamLevel, back.go, chromeTimer, moreOpen, isPlaying, togglePlayPause, navigateSubtitle, isYtMode, chromeShadowing, practiceOpen`。**没有 index，也没有那个函数**；`:738` 还挂着 `eslint-disable react-hooks/exhaustive-deps`。
- `frontend/src/components/watch/WatchChromeProvider.tsx:82-86`（`publish` 浅比较直接 return）+ `:113-116`（页面每次都发布同一个 memo 对象）→ 过期对象**不会**被后续渲染刷新。
- 对照组 `page.tsx:732` —— `onPrev: () => navigateSubtitle(-1)`；`navigateSubtitle` 是稳定 `useCallback` 且读 **ref 镜像** `currentSubtitleIndexRef`（`useVideoPlayer.ts:506-523`、`:179-185`）→ **「上一句」不会过期**。这正是用户感觉两个按钮表现不一致的来源。

实测（414×896 / iPhone UA / 本地 dev，`probe_watch2.js`，真实 `touchscreen.tap` 点按钮中心）：

| 步 | 计数 | 高亮项 | video.currentTime |
|---|---|---|---|
| 初始（断点续播 t=30） | 10 / 190 | 9 | 30.05 |
| 点「下一句」 | **2 / 190** | 1 | **3.48**（往回跳 8 句） |
| 再点 | 3 / 190 | 2 | 6.73 |
| 再点 | **3 / 190（不动）** | 2 | 6.56 |
| DOM 直点 ×4（绕过浮层） | 4 → 5 → 6 → **6（不动）** | 3→4→5→5 | 9.7 / 13.1 / 16.5 / 16.3 |

- 「回退 8 句」= memo 里冻结的 index 是 0（首次渲染值），点击目标恒为第 2 句 `start_time=2.68`。
- 「时好时坏」= 任何一个依赖项变化都会重建 memo：播放/暂停（`isPlaying`）、⋯ 面板、跟读抽屉、切级别、处理中轮询；iOS 路径下 `seekTo` 还会 `pause()+play()`（`useVideoPlayer.ts:473-475`）→ 一次 seek 制造两次 `isPlaying` 翻转，碰巧就把闭包刷新一次。
- 结果：**「下一句」会一次对、一次错、然后卡住**，且**首次点击常常是往回跳**——用户看到的正是「跳转不正常 + 按了没反应」。

### 2.2 P1：「上一句」被 Next dev 指示器吃掉（仅 dev，实测）

- `frontend/next.config.js` 没有 `devIndicators` → Next 16 默认 `{ position: 'bottom-left' }`（`frontend/node_modules/next/dist/server/config-shared.js:117-119`；文档 `node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/devIndicators.md`：默认 `bottom-left`，可改 `bottom-right` 或 `false`）。
- 实测（`probe_watch3.js`，414×896）：底栏 `watch-prev` rect = `[0, 840, 104, 56]`，其中心点 `(52, 868)` 的 `elementFromPoint` = **`NEXTJS-PORTAL`**（badge `div.nextjs-toast` rect = `[20, 840, 36, 36]`）；同一时刻 `watch-toggle-play` / `watch-next` / `watch-shadowing` 的中心点都命中它们自己。
- 生产构建不注入该指示器（`devIndicators` 只在 dev 生效）→ **这就是用户猜的「开发环境和生产服务器环境的差异」里唯一成立的那一条**。
- 真机联调同样中招：`docs/design/mobile/app-shots/13-device-414-first-screen.jpg` 与 `14-414-first-screen.png` 左下角那个黑色「N」就是它。
- 附注：「上一句」在第 1 句时本来就无事可做（`navigateSubtitle` 有 clamp，`useVideoPlayer.ts:513-517`），这是正确行为。

### 2.3 P1：字幕跳转与高亮——错的是「下一句」，不是点文稿

- 高亮索引的**唯一写入者**是播放 tick：`page.tsx:280-290`（`findSubtitleIndex` → `setSubtitleIndexRef.current`），`<video onTimeUpdate>` (`:1002-1006`) + 250ms 轮询 (`useVideoPlayer.ts:411-417`) 双路。点文稿写一次 index（`page.tsx:1341-1344`），随后由时间反推覆盖 → 只要 seek 到的是过期句，卡片计数/高亮/画面就一起错。
- 实测点文稿第 30 / 12 / 60 句：`30/190 → 31`、`12/190 → 13`、`60/190 → 61`（200ms 内跳到位、高亮跟随）→ **HTML5 后端下「点文稿跳转」本身是好的**；用户看到的「跳转高亮不正常」是 2.1 的连带，不是点文稿这条路径坏了。
- 两个次要因子（未构成主因，一并记下）：
  - `findSubtitleIndex` 落在句间空隙返回 `-1`，页面忽略 `-1`（`page.tsx:284-285`）→ 空隙里高亮停在上一句；
  - 自动居中 effect 只依赖 index（`page.tsx:433-444`），播放中每句 `smooth scrollBy` 会抢用户的手动滚动，手指落点可能滑到邻句。

### 2.4 P1：两个容器边界突兀（实测几何）

414×896 实测（`probe_watch2.js` 的 GEOMETRY）：

| 元素 | rect | 规格 |
|---|---|---|
| 画框 `[data-testid=video-frame]` | `x=0 y=44 w=414 h=232.9` | 满宽出血、直角、`bg-surface-dark` |
| 当前句卡 `[data-testid=current-sentence-card]` | `x=0 y=288.9 w=414 h=108` | `mt-3`(12px) 断层、**满宽直角**、1px 全边框、`bg-canvas` |
| 文稿面板 `aside` | `x=16 y=396.9 w=382 h=615` | **内缩 16px**、圆角 22px、1px 边框、`bg-canvas` |

- 关键：**卡片底边 y=396.9 与面板顶边 y=396.9 完全相接（0 间隙）**，两条 1px `border-hairline` 叠在一起；卡片是「满宽直角带」，面板是「内缩圆角卡」，两种容器语言同屏，而三个面都是纯白 → 白底上只剩两条边界线 → 「突兀」。
- 用户截图与本地 e2e 产物 `docs/design/mobile/app-shots/14-414-first-screen.png` **完全同构**（同一句 "But I think you're coming at it from the wrong perspective."、同一个 `1 / 190`、同一条高亮项）→ 该截图来自本地 dev（或指向 dev 的局域网手机），不是生产。

### 2.5 P2：进度条时长（数据 + 一行代码）

- DB 行 `duration=612.0`；`ffprobe backend/media/6fdcdd86-….mp4` = **719.98s**；字幕最后一 cue 结束于 612.27。
- `page.tsx:729` 把 `video.duration`(612) 交给 store，`WatchBottomBar.tsx:81,121` 优先用它算总长 → 实测 `aria-valuemax="612"`、`progress-time` = `0:15 / 10:12`、填充宽 = `15.76/612`。**进度条在 612s 就 100%，最后 108s 既没有进度也没有字幕**。
- 媒体是手工塞进 `backend/media/` 的（同字节还以 `98c5e214-…_raw.mp4` 存在，且没有对应 Video 行），所以是「行没跟着文件更新」。

## 3. 「开发环境 vs 生产服务器」到底差在哪（用户假设的核验）

| 维度 | dev（本机 :3000） | 生产 | 能否解释现象 |
|---|---|---|---|
| **代码** | `next dev` 现编译工作区；本次 UI（`WatchTopBar` / `WatchBottomBar` / `CurrentSentenceCard` / `WatchChromeProvider` / `WatchMoreSheet`）**全部未提交**（`git status` 为 `??`），`page.tsx` 相对 HEAD 改 498 行 | **用户 10-02 确认：生产构建就是最新的**（由 `Dockerfile.prod` 从工作区 `COPY . .` 构建）→ 生产的播放页**有**这套组件 | **否**：版本差被排除 —— 也就是说 **P0 的过期闭包在生产同样存在**（同一份代码），而「上一句被 dev 指示器吞掉」才只在 dev 出现 |
| **数据** | 本地 DB 只有 1 条视频 = 截图那条（190 句 / 612s） | `https://seeword.top/api/v1/videos/6fdcdd86-…` → **404**，`/media/6fdcdd86-….mp4` → **404**；公开列表是另外 3 条真实 YouTube 视频 | **是**：截图状态只可能来自本机 dev（用户确认手机直连局域网 dev） |
| **运行时浮层** | Next dev 指示器 36×36 压在「上一句」中心（2.2） | 生产不注入 | **是**：这是唯一一条真正的「dev 才坏」 |
| **视频源形态** | 本机这条有真文件 → HTML5 `<video>`，`sentenceNavDisabled=false` | 生产多数条目是 YouTube 源；**下载失败过一次的视频行 `video_url_*` 全空** → `isYtMode=true` → `sentenceNavDisabled=true`，两个句按钮**被设计成置灰不可点**（`page.tsx:734`），且进度条整条失效 | **是（待在生产核验）**：同一个用户在生产点开另一条视频时，「上下句」可能本来就是灰的 |
| **React StrictMode** | Next 16 App Router 在 dev 默认开启（`next.config.js` 未设 `reactStrictMode`） | 生产关闭 | **否**：`WatchChromeProvider` 的模拟重挂载会在同一帧内重发布，不留下死按钮 |
| **API/媒体代理** | dev 只有 `rewrites()` 把 `/api`、`/media` 转 `localhost:8000`（`NODE_ENV=production` 时为空数组，生产由 nginx 代理） | nginx 反代 + `proxy_cache` | **否**：两边都是同源相对路径；但**手机直连局域网 dev**（`192.168.x.x:3000`）时 rewrite 的目标写死 `localhost:8000`（`next.config.js` 里 `allowedDevOrigins` 默认放行 `192.168.*.*`），用户实测这条路径可用 |

**结论**：用户「像是环境差异」的直觉**对了一半**——dev 指示器确实吃掉了「上一句」的点击（仅 dev）；但「下一句往回跳 / 按了没反应」是代码缺陷，生产用的是同一份代码，会同样发生；「边界突兀 / 开关割裂」是设计。**另需在生产核验一条**：生产那些 YouTube 源（无本地文件）的视频，两个句按钮本来就是置灰的——如果你是在生产上点开另一条视频看到「按钮没反应」，那是另一条独立原因（见上表「视频源形态」）。

## 4. 修复方案

### 4.1 P0：「下一句」过期闭包（三个选项，推荐 A）

- **A（推荐）稳定引用 + ref 读最新值**：页面里
  `const nextRef = useRef(handleNextSubtitle); useEffect(() => { nextRef.current = handleNextSubtitle; }); const onNextStable = useCallback(() => nextRef.current(), []);`
  `chrome` 用 `onNextStable`。
  - 理由：与现有 `navigateSubtitle` 的 ref 镜像同一先例（`useVideoPlayer.ts:179-185` 的注释就是为这个坑写的）；
  - 保住 store 的硬约束「高频读数绝不进 store」（`WatchChromeProvider.tsx:28-31`）：chrome 对象不再随 index 变化，壳不会每句重渲染；
  - 保住 `handleNextSubtitle` 里的跟读状态重置（`reRecord` / `shadowingSaved` / `lastAttemptId`）。
- **B 一行版**：`onNext: () => navigateSubtitle(+1)`（与 `onPrev` 对称）。代价：丢掉上面那三个跟读重置，要保留就得把它们搬到「index 变化」的 effect 里。
- **C 全量依赖版**：把 `currentSubtitleIndex` / `handleNextSubtitle` 加进 memo 依赖。能修好，但壳每秒重渲染 4 次，违背 store 的低频约束。
- **配套**：在 `WatchChromeProvider.tsx` 顶部注释里加一条硬规矩（并考虑做成 INV）：**store 里只放稳定引用的句柄或 ref 读值，禁止直接塞读组件状态的闭包**——这次的坑正是「按 ref 镜像写 onPrev、按闭包写 onNext」的不对称。

### 4.2 P1：dev 指示器挪位（仅 dev 体验）

- `frontend/next.config.js` 增加 `devIndicators: { position: 'bottom-right' }`（或 `false`）。
- 理由：默认 `bottom-left` 与观看页底栏「上一句」100% 重叠（实测），真机局域网联调同样中招；它还会污染一切「点底栏左侧」的自动化断言。
- 注意：这是 dev 配置，不改变生产行为，但要顺手在 `.agent/state.md` 记一笔「真机联调时左下角是 dev 指示器，不是产品按钮」。

### 4.3 P1：画框 ↔ 当前句卡 的边界 + 模式开关割裂（**已出五条路线原型，见 §7**）

一句话：**把「当前句 + 文稿」并成一张面、把模式开关上移成这张面的面头**（原型 R1）。
下面三个旧选项只保留了结论性的一句；可运行、可量、带截图的完整对比在 §7 与
`docs/design/mobile/prototypes/R-reading.html`。

- ~~选项 1（去边框）~~ → 升级为原型 **R4**（最小改动版，仍然两个盒子、开关仍夹在中间）。
- ~~选项 2（卡贴画框）~~ → 就是原型 **R1** 的「面从画面下沿长出来」，只是当前句现在与文稿同面。
- ~~选项 3（两容器统一规格）~~ → 与原型 **R3**（字幕带）同方向，但它保住了「画面块 / 文稿卡」两块各司其职。
- 无论选哪个：**这是一次版式决议**，按仓库规矩要走 `/decision-support` 落一条 DEC，并同步 INV-021/022/024 的措辞与对应 spec。

### 4.4 P2：进度条时长

- 数据侧：把该行 `duration` 与媒体对齐（或重跑一次 ingest 元数据），否则最后 108s 没有字幕也没有进度；
- 代码侧（可选）：`WatchBottomBar` 的 `total` 改为**优先真实媒体** `videoRef.current.duration`，`duration` 只做兜底（现顺序 `useVideoPlayer` 后再兜底 `video.duration` 是反的）。改它要有断言。

### 4.5 P2：文稿列表跟随滚动

- （可选）用户手动滚动后 2s 内暂停自动居中；或在 `pointerdown` 期间冻结。

## 7. 版式提案：画框 → 当前句 → 文稿（2026-10-02 追加）

**原型**：`docs/design/mobile/prototypes/R-reading.html`（七条路线并排 + 实测数字表 + 六条硬约束），
可单独打开的变体 `R0-today.html` / `R1-sheet-head.html` / `R2-sheet-now.html` / `R3-band.html` / `R4-min.html` / `R5-flush.html` / `R6-band-meta.html`，
静态图 `shots/R0..R6.png`（414×896 @2x，由 `_reading-shots.js` 渲染）。
数据是本地库那条视频的**真实前 5 句**；画面是从 `app-shots/14-414-first-screen.png` 裁下来的真实帧。

### 7.1 问题拆成两句

- 「画框 ↔ 当前句卡 边界突兀」：当前句卡是**出血直角带 + 1px 上下边框**，文稿面板是**内缩 16px 圆角卡**，
  两者底/顶边落在**同一个 y（实测 396.9）** → 白底上两条发丝线相撞；这一段里同时存在三套容器语言。
- 「模式开关割裂上下文」：开关（3 个 chip + 折叠键）自带一个卡片的头部，被夹在「当前句」与「文稿」两块**内容**中间。

### 7.2 六条硬约束（先查后设计，否则版式白做）

| 约束 | 出处 | 钉住什么 |
|---|---|---|
| 卡与画框**同 x 同宽** | `mobile-current-sentence-card.spec.ts:152-156` | `|card.x−frame.x|≤2`、`|card.width−frame.width|≤2` → 卡不能内缩 |
| 卡顶与画框下沿**间距 0…16px** | `mobile-inline-subtitle.spec.ts:113-114`（另一条给到 +24） | 齐平可以；被包进更靠下的面（R1 的 +31px）就红 |
| 露出画面 ≥120px | `mobile-player-shell.spec.ts:169` | 画框之上不许再加东西 |
| 卡内下 1/5 **不许放控件** | `mobile-current-sentence-card.spec.ts:232` | 取样点 `(75%, 80%)` 只能是「播放/暂停」 |
| 计数**在卡内且全页唯一** | `mobile-current-sentence-card:173` · `mobile-inline-subtitle:171` · `watch.spec.ts:106-116` | `1 / 190` 不能搬出卡，也不能出现两份 |
| 模式行仍是 **tablist** | `watch.spec.ts:45,78-90`（1280 与手机档都跑） | `role=tablist/tab` + 三个标签 + `aria-selected` 不能换 |

另有两条只跑桌面：折叠键 `aria-label="收起为字幕轨"`（`repro-stage1.spec.ts:95-109`）⇒ **移动端删掉折叠键是安全的**。

### 7.4 推荐 R5「齐平字幕带」，四条理由

1. **边界消失**：字幕带与画框**齐平**并去掉外框 → 画框下沿就是唯一的边，不再有「12px 白缝 + 两条封边线」。
2. **开关归位**：模式行进文稿卡的卡头（发丝线上下分隔的工具栏），它是「文稿这个容器的工具条」，而不是夹在两块内容中间的 chip 行 → 用户不再看到「字幕 → chip 行 → 字幕稿」的三段式。
3. **顺手修两个真问题**：折叠键在移动端没有对象（≤1023px 下折出的竖轨并不真的让出一列，且无 spec 依赖）；chip 行仅 32px 高、不到 44px 触控基线，换分段控件补上。
4. **零断言代价**：六条硬约束一条不碰（同 x 同宽 ✓、0 ≤ 16 ✓、露出画面 233 ≥ 120 ✓、计数仍在卡内且唯一 ✓、仍是 tablist ✓、卡内下 1/5 无控件 ✓），且比现状少 12px、首屏文稿仍 4 条。

### 7.5 三件已定案（用户 2026-10-02 拍板，按推荐执行）

1. **断层 = 0**（字幕与画框齐平）：只有 0 能让边界这件事消失；真机若嫌挤，6–8px 仍在合法窗口（0…16）。
2. **重复 = 降级文稿里的当前项**：`bg-surface-soft` 淡底 + 保留 3px 橙色左竖线 + 文字 `text-ink`，橙色只留给字幕带。
3. **⋯ 面板里那份「语言」= 保留**（设置面板的完整入口 + 卡头快捷方式，共享同一个 store）。

**执行方案**：`knowledge/plans/移动端播放页-句导航与R5版式-执行方案-2026-10.md`（含 T0–T6 任务、精确改动位置、验收判据与命令、风险与回滚）。

### 7.6 落地顺序（建议）

先落 §4.1（P0 过期闭包，1 行 + 回归）→ §4.2（dev 指示器，1 行）→ 再走 `/decision-support` 定版式（R5 或 R3；R1/R6 要额外改断言与 INV 措辞）→ 最后才是 P2（时长数据、滚动抢手）。**理由**：前两条是纯缺陷、零设计争议；版式即使选 R1 也只涉及 2–3 条断言与 INV 措辞，先把「按了没反应」这个更痛的问题按死。
