### T2 · P0：「下一句」过期闭包（≈10 行）

**根因**：`page.tsx:733` `onNext: handleNextSubtitle` —— 它是每次渲染新建、闭包读 `currentSubtitleIndex` 的普通函数，而 chrome memo（`:739-751`）的依赖表里既没有它也没有那个 index；`WatchChromeProvider.publish` 浅比较直接 return（`:82-86`）⇒ 过期对象永久驻留。实测：10/190 点一次往回跳到 2/190，再点点不动。

**改法**（`frontend/src/app/(main)/watch/[id]/page.tsx`）：在 `handleNextSubtitle`（`:639-653`）定义之后、chrome memo（`:716`）之前插入：

```tsx
// onNext 必须与 onPrev 对称：store 里只放**稳定引用**，闭包经 ref 镜像读最新状态。
// （第一版把 handleNextSubtitle 直接塞进 store：它闭包里的 currentSubtitleIndex 冻结在
//   memo 上次重算的那一刻，实测「下一句」会往回跳，然后彻底不动。）
const nextRef = useRef(handleNextSubtitle);
useEffect(() => {
  nextRef.current = handleNextSubtitle;
});
const onNextStable = useCallback(() => nextRef.current(), []);
```

chrome memo 里 `onNext: handleNextSubtitle` → `onNext: onNextStable`，并把 `onNextStable` 加进依赖表。
**不要**把 `currentSubtitleIndex` / `handleNextSubtitle` 加进依赖表 —— 那会让壳每句重渲染 4 次，违背 store 的低频约束（`WatchChromeProvider.tsx:28-31`）。

同时在 `WatchChromeProvider.tsx` 顶部注释区补一条硬规矩（T5 里做成 INV-025）：
**store 只承载稳定引用或 ref 读值；凡读组件状态的闭包，一律先做 ref 镜像再进 store。**
