## 二、R0 治理收尾

**结论（10-12 终局）：已完成，治理已对齐。** 过程值得留档，因为它推翻了一个看起来像死路的判断：

1. `.agent/state.md` 曾记明残留是 `.claude/settings.local.json`（git 未跟踪的本地文件）被报为
   `code_missing` + `code_unbaselined`，而三次 `aoci_maintain` 的 write 集里始终不含它。
2. Guide 仍给 `complete=false` / `next_action=call_no_argument_aoci_maintain_for_current_machine_batch`，
   于是按它的 `next_action` **第四次**调用 `maintain`：这次签发了 10 条批次（规则层重构 B 的受管理对象），
   `aoci_update_entry` 整批提交后 `applied=10` / `remaining=0` / `aligned=true`；第五次 `maintain`
   候选为空、`governance_aligned=true`、`next_required_action=none`，残留对象也不再出现在 drift 里。
3. **教训**：`guide.complete=false` 只说明还有 executable targets，**不等于不可对齐**；
   「不重复 `maintain`」只适用于已经 `aligned=true` 之后。先按 Guide 的 `next_action` 再跑一次才是正确动作。

动作：

1. 已执行：`maintain` → 整批 `update_entry` → `verify` / `check` / `guide` 三步验证。
2. **判据**：`governance_aligned=true` 且 Guide 的 `next_required_action=none`（本片已满足）。
3. 仍然不做：不手改 `.aoci` 白名单、不合成 candidate、不用 `scan --force` 洗白。同类漂移复发的路径仍是
   `maintain` → 真读证据 → 整批 `update_entry`。
4. 顺带核实：该文件既未跟踪也不被忽略（`git status` 报 `??`），说明它是本机工作产物——把它
   纳入版本控制或让它退出托管范围都属仓库决定，不是本次重构能顺手做的。

## 三、R1 会话开场降级（改 `AGENTS.md`）

1. 「开场三件事」第 1 步改为分档：
   - **只读问答 / 查文件 / 解释代码** → `aoci_search` / `aoci_get_entries` 定向取；
   - **要改代码、要做系统级判断、要重建或恢复系统全貌** → `aoci_rules` → 全量 `aoci_overview`，
     并原样跟随 `next_cursor` 直到 `completed`。
2. MUST 节保留「建立或重载系统认知时 MUST 先 `aoci_rules` 再 `aoci_overview`」，但**补上触发
   条件**，不要让它被读成"每次会话"。
3. `<!-- aoci:begin -->` 与 `<!-- aoci:end -->` 区块**逐字节保留**。
4. **判据**：新会话做只读问答时，工具调用里不再出现全量 `aoci_overview`；做代码改动时仍然出现。
5. 需要配一张 DEC（改的是宪法级文件）。

## 五、R3 门禁减重

1. `ci.yml` 三个 job 各加自己的 `paths`：
   - backend → `backend/**`、`backend/requirements*.txt`、`backend/pyproject.toml`、
     `backend/pytest.ini`、`backend/.mypy-baseline`；
   - frontend → `frontend/**`；
   - e2e → 跨端变化（两端同时改，或 `docker-compose*.yml`、`nginx*.conf` 等）。
2. **陷阱**：若这些 job 在分支保护里是 required status check，被 skip 的 job 会一直挂"未完成"，
   PR 反而卡死。落地时要么同步调整 required checks，要么把判断挪进 job 内部早退；把这条写进
   workflow 注释（照 `knowledge.yml` 那种"为什么这么做"的注释风格）。
3. `AGENTS.md` 的 MUST 节措辞对齐事实：机器强制（12 个测试套 + 2 项检查）与评审强制（11 条）
   分开写，不再统称「强制执行」。
4. **判据**：单端改动只触发一个重 job；MUST 节里不再把 review-only 称作强制执行。
