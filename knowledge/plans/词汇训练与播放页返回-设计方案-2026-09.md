## 2. 播放页返回导航（确认 = 方案 A）

- **「返回」= 回到来处**（动态目标）；**「去频道」= 一次导航**（固定 `/channels/{slug}`）。两者分开。
- 每个入口打来源标记：

| 来源标记 | 返回目标 | 按钮文案 |
|---|---|---|
| `from=home` | `/` + 原筛选 query | 返回首页 |
| `from=channel&slug=xx` | `/channels/xx` | 返回频道 |
| `from=set&set=xx` | `/vocabulary/sets/xx` | 返回词库 |
| `from=drill` | `/vocabulary/drill`（恢复未完成轮次） | 返回训练 |
| `from=search` | `/search?q=…` | 返回搜索 |
| `from=favorites` | `/favorites` | 返回收藏 |
| 无标记 | `router.back()`；无法回退则 `/` | 返回 |

配套：

1. **筛选进 URL**：`category / level / sort / q` 写进 query，`router.replace`。
2. **滚动恢复**：列表页把 `scrollY` 存 `sessionStorage`（key = 完整 URL）。
3. **用 `replace` 而非 `push`**：避免「首页 → 播放页 → 首页 → 浏览器返回 → 又回播放页」的回退环。
4. 顺带修：处理失败页 `push("/browse")`（`:588`）、已下架页出口（`:550-553`）、无频道也显示「返回频道」（`:693-696`）。

### 2.1 频道入口（确认 = 边框 chip + 朝右箭头）

meta 行的频道名（`watch/[id]/page.tsx:684-697`）升级为带边框 chip + 箭头图标（**朝右**，朝下会被读成"展开菜单"），不新增占位。

### 2.2 首页排序新增「收藏最多」+「本周收藏」（已确认：两个都加）

**排行榜现在的做法**（`services/ranking_service.py`）：

- 三个 scope：`latest` / `weekly_views` / `weekly_favorites`，每个算 **Top-20**。
- 周界：**北京时间本周一 00:00**（`ranking_service.current_week_start_utc()`，固定 UTC+8）。
- 本周收藏口径：`user_favorites.created_at >= 本周一` → `GROUP BY video_id` → `COUNT(*)`（`ranking_service.py:137+`）。
- 可见性过滤三元组：`is_official + is_published + status ∈ (ready, ready_subtitles)`。
- **缓存方式**：结果存 Redis 快照 `rankings:snapshot:{scope}`（TTL `rankings_snapshot_ttl_seconds`），Celery beat 每天本地午夜后跑 `snapshot_rankings` 重算覆写；Redis 挂了 fail-open 直接查库。
- 入口：`GET /api/v1/videos/rankings?scope=…`。

**为什么不能直接复用快照**：快照只存固定 Top-20，而首页是**带筛选的分页列表**（`GET /api/v1/browse/feed`），需要能排序的 SQL。所以首页复用排行榜的**口径**，不用它的缓存机制。

**实现方式**（改动很小）：

| 排序项 | 排序依据 | 成本 |
|---|---|---|
| 收藏最多（总量） | `Video.favorite_count DESC`（去规范化计数，`models/video.py:131` 现成） | 极低，加一个 order_by 分支 |
| 本周收藏 | `LEFT JOIN (SELECT video_id, COUNT(*) FROM user_favorites WHERE created_at >= 本周一 GROUP BY video_id)` → 按 metric DESC、nulls last | 低，需要一个 `user_favorites(created_at)` 或 `(video_id, created_at)` 索引（表很小，可先不加） |

两者都**沿用排行榜的周界函数与可见性三元组**，保证同一口径。

要动的点：

1. 后端 `api/v1/browse.py:100` 的 `sort: Literal["latest","hot"]` 加两个值，排序分支加在 `:51`；**周界直接调 `ranking_service.current_week_start_utc()`**。
2. 前端 `hooks/usePlatformFeed.ts:17` 的 `FeedSort` 加两个值，`HomeFilterBar` 的 `SORT_OPTIONS`（`components/home/HomeFilterBar.tsx:29-32`）加两个选项。
3. 首页默认流（推荐）走 `/api/v1/recommendations/home`（`usePlatformFeed.ts:88-95`）；**选了新排序就自动落到 `/browse/feed`**，无需额外改动。
4. `browse/feed` 的缓存键已含 `{sort}`（`browse.py:35`），新增排序值不会串缓存。

## 4. 训练流程改为选择题（确认）

### 4.1 取消「认识 / 不认识」

理由（用户原话归纳）：选择题更快更省事；能客观验证真会还是假会（选对即知道、选错即不知道）；「认识/不认识」只在快速刷简单词时有优势，学新词时作用很小；词库里的「标记已掌握」已在浅层判断上替代它。

→ `components/vocabulary/WordFlashcard.tsx` 的双按钮形态**整体废弃**；`drill` 的「闪卡学新词」与「复习测验」两阶段（`drill/page.tsx:98-235`）合并为**一条全程选择题的循环**。

### 4.2 作答后的反馈（确认 = 选项 1）

1. 标出对错（选中项变红/绿，正确答案高亮）；
2. **展开完整释义**：词性、音标、中文释义、例句；
3. 有原句时显示原句 + 「去原视频」入口（§6.1）；
4. 底部「下一个」，**必须手动点击**才推进。

### 4.3 新词首次出现带原句

首次出题时题干带该词所在的字幕原句（词高亮），用户可从语境推断，而不是 25% 靠蒙；干扰项优先取自同一视频（§8）。

### 4.4 同一个词重复出现时换题型（默认生效）

| 出现次序 | 题型 |
|---|---|
| 第 1 次 | 英 → 中（识义） |
| 第 2 次 | 中 → 英（4 个英文词） |
| 第 3 次及以后 | 听音选词 / 英 → 中（选项重新打乱） |
| 已较熟时（可选） | 拼写（`see_meaning_spell_word`，已有实现） |

三种都属选择题，不涉及拼写填空；不采用拼写时填空/听写留到 §9。

## 5. 训练调度算法（确认：无层级）

### 5.1 唯一状态：连续答对计数 c

**取消五档熟练度**（用户明确：层级从 -2 升到 2 要答对三四次，太啰嗦）。每个词在本轮只维护一个计数：

| 事件 | 结果 |
|---|---|
| 答对 | c += 1 |
| 答错 | **c = 0（重新计算）** |
| **毕业** | **c == 2（连续两次答对）** → 移出本轮队列 |

例：`对 → 错 → 对 → 对` 才毕业（对错对不毕业）；`对 → 对` 即毕业。

### 5.2 出现间隔（答完后重新插回队列的位置）

| 刚发生 | 下一次出现 | 理由 |
|---|---|---|
| 答错（c 归 0） | 隔 **1 题** | 错的词立刻再考，符合「选错了更要多过」 |
| 答对（c = 1） | 隔 **5 题** | **不能紧接着问**——紧接着问是短时记忆，答对不算数；隔开 5 题后还记得，才构成"连续两次答对" |
| 毕业（c = 2） | 不再出现 | — |

「隔 5 题」是按上述理由定的尺寸，可调（3~8 之间都不影响机制）。

### 5.3 一轮的规模

10 个词的队列：一次不错的词答 2 次，错过的词答 3 次以上 → 一轮约 **23~30 题**，按每题 10~15 秒估约 **5~8 分钟**。加练一轮同理。

### 5.4 复习调度：错误次数决定复习频率（确认方向）

**10 个新词是"学"；复习是另一条线。**

新增字段：`wrong_count`（累计答错次数）、`last_wrong_at`、`round_wrong`（本轮内是否曾答错，用于决定第一次复习的间隔）。

| 情况 | 下次复习 |
|---|---|
| 本轮内**答错过** | **次日**（1 天）必进复习队列 |
| 本轮内**一次没错** | **3 天后**进复习队列 |
| 复习时答错任意一次 | 回到 **次日**（1 天），`wrong_count += 1` |
| 全对且 `wrong_count = 0`（干净词） | 3 → 7 → 16 → 35 天 |
| 全对但 `wrong_count ≥ 1`（易错词） | 2 → 5 → 12 → 25 天（比干净词短一档） |
| `wrong_count ≥ 3`（老大难） | 间隔上限压到 **7 天**，反复出现 |

**同日内的复习优先级**：`last_wrong_at` 是昨天的词排最前 → 再按 `wrong_count` 降序 → 再按到期时间升序。这样"前一天错得多的词"第二天第一屏就出现。

**实现说明**：现行 SM-2 的 interval 是 `1 / 6 / interval × ease_factor`（`sr_service.py:47-64`），与上表不同。方案是**用上表直接计算 `interval_days` 与 `next_review_at`**，保留 SM-2 的所有列（`ease_factor` 不再参与计算，留作兼容/显示）。这是一次算法替换，需要 DEC 条目。

### 5.5 落库结构

- 新增 `study_sessions`：`user_id, local_date, kind(daily|extra), target_count, done_count, correct_count, status(active|finished|abandoned), started_at, finished_at`
- 新增 `study_session_items`：`session_id, vocabulary_id, correct_streak, wrong_in_round, status(pending|learning|graduated)`（**每词一行，反复作答是 UPDATE**）
- `vocabulary` 增列：`wrong_count`、`last_wrong_at`
- 进入 `/vocabulary/drill` 先查「有没有未完成的一轮」，有就续上（解决刷新/切页丢进度）。

- 播放页返回按钮 → 回 `/vocabulary/drill`（`from=drill` 标记）→ 训练页读未完成轮次**续上**
- 播放页读 `?sub=` 定位到该句、高亮该句、高亮该词（`?word=` 现在被忽略）

**四件前置**（缺一不可）：

1. **词→句链路**：前端点字幕加词时传 `subtitle_id`（`hooks/useWordLookup.ts:111-125`）、过筛建词补写（`vocab_set_service.py:143-171`）；
2. **存量回填**（确认：全量补）：按 `(video_id, context_sentence)` 在 `subtitles` 表匹配，匹配不到的保持为空（按钮不显示）；
3. **播放页 `?sub=` / `?word=` 定位与高亮**；
4. **轮次落库 + 来源标记**（§2、§5.5）。

**否决记录**：乙（新标签页）——移动端多一个页签、需手动关闭，体验差；丙（页内小窗）——播放器是 735 行的页面级逻辑（`hooks/useVideoPlayer.ts`），嵌入小窗会损失真实视频观感与质量。

### 6.2 「回到对应句子」的入口分布（确认）

| 位置 | 是否加 | 做法 |
|---|---|---|
| 训练页（作答后 / 释义区） | **加** | 跳到播放页并定位（甲，`from=drill`，回来续轮） |
| 视频集合详情页（`sets/[id]`） | **加** | 跳播放页定位（该页无瞬时进度，跳走无损）：`?t=&sub=&word=&from=set&set={id}` |
| 词库「全部单词」 | **不加** | 已确认「怎么加都不好」 |
| 词库「按视频」分类 | **不做** | 跳转入口砍掉后只剩标签作用 |

### 6.3 进度落库的服务器成本（甲方案的前提，已核算）

**结论：可忽略，不需要新服务、不需要 Redis。**

关键前提：**现有代码本来就每答一题写一次库**（`drill/page.tsx:164` 每次点认识/不认识都发 `POST /vocabulary/{id}/review`）。所以"进度存服务器"不是新的写入模式，只是每次多写 1~2 行。

| 项 | 每轮行数 | 每用户/年 | 100 活跃用户/年 |
|---|---|---|---|
| `study_sessions` | 1 | ~1,100 行 ≈ 0.3 MB | 33 MB |
| `study_session_items` | 10 | ~11,000 行 ≈ **3.3 MB** | 330 MB |

- **内存**：活跃工作集 = 活跃用户 × 10 行，几十 KB，不挤转码的 Whisper（1.5 GB）。
- **磁盘**：330 MB/年（100 用户），对比视频媒体 17.5 GB 差 50 倍；且可**封顶**：一轮完成时顺手删该用户 30 天前的轮次明细。
- **CPU**：每次作答 1~2 次 UPDATE，30 人同时练约 2.5 写/秒，对 Postgres 是噪声级。
- 即使不跳走，落库仍然必要：iOS Safari 会丢弃后台页签、用户会刷新、次日复习与「今日已学 N 词」需要服务端数据。

### 7.3 快速过筛（确认：不改流程 + 加告知）

- **保持**会/不会两阶段判定不动。
- **补告知文案**：过筛页需明确提示「标为『会』的词将**不计入学习计划**，不会再出现在训练队列里」。这句话现在没有。
- 好消息：**行为其实已经是现状**——判「会」会置 `mastery_level = mastered`（`vocab_set_service.py:481-484`），而新词队列只取 `new`、复习队列排除 `mastered`（`vocabulary_service.py:121-140`），所以它已经被排除在训练计划外。**唯一缺的是告知**。
- 附建议：给「已掌握」提供**取消标记**入口。过筛是快速连点操作，误点后目前无法退回（`POST /vocabulary/{id}/mastered` 只能置位），只能删除该词——这是个真实的误操作风险。

### 7.4 一词多视频：不做多来源（确认）

用户的学习是单线程的（一次一个视频），且「回到对应句子」只存在于集合里、集合天然绑定一个视频，**没有歧义**，因此不需要 `word_occurrences` 多来源表。`Vocabulary.video_id / subtitle_id` 保持「首次加入时的来源」语义，唯一约束 `(user_id, word)` 不变。

## 8. 四个选项从哪来（已确认按此顺序）

### 8.1 四条硬原则

1. **同词性**——否则「只有它是动词」就能排除；
2. **长度与难度接近**——否则最长/最短那个一眼像答案；
3. **语义相关但不重叠**——必须真认识才能选对；
4. **不存在两个都讲得通的选项**——否则选对也被判错。

### 8.2 干扰项来源（按优先级，已确认）

| 优先级 | 来源 | 为什么 |
|---|---|---|
| **1** | 同一个视频里、同一等级、同词性的其它已加入词 | 视频话题集中，干扰项"看起来都在这个视频里出现过"，蒙不出来 |
| **2** | 用户词库中同等级、同词性、拼写相近（编辑距离 2~4）的词 | 专门制造形近词混淆（affect / effect、record / report） |
| **3** | ECDICT 同考试等级、同词性的高频词 | 兜底，给词库还很小的人用 |

### 8.3 硬约束

必须凑够 4 个选项（按 1→2→3 逐级补齐）；排除与正确项释义互为同义/包含关系的候选；重复释义去重；选项每次洗牌（`shuffle_options` 已有，`practice_service.py:52-56`）。

**现状的坑**：`practice_service.py:72` 候选不足 2 个时直接 `options=None`，题都出不来——必须修掉。

### 8.4 工程量

需要重写一个**独立的干扰项选择函数**（输入：目标词、用户词库、ECDICT、同一视频字幕词；输出 3 个干扰项），并把「按轮次选题型」接上（现在是按 mastery 随机）。这是本议题后端的主要工作量。

### 8.5 防蒙设计

4 选 1 蒙对率 25%，但**毕业要求连续两次答对**（且第二次间隔 5 题、题型可能轮换），蒙对的词几乎必然暴露 → 综合蒙混过关率约 6% 且不持久。
