## 0. 总体判断

规模的证据摆在那儿：92/92 项需求、约 190 个 API 端点、47 个 service、33 个 model、85 个测试、
71 个迁移。业务纵深（视频处理、词级标注、筛词闭环、训练调度、管理后台）是这个项目最强的部分。

短板集中在三处：

1. **入口漏斗**：注册到「第一次感受到产品魔法」之间的路太长，且有静默失败。
2. **接缝设计不足**：前后端之间的状态、能力、契约没有单一主人，靠约定和重复代码撑着。
3. **产品面与目标用户的错位**：对外说的是「四六级用视频背单词」，考试侧功能却只覆盖阅读。

下面按 A–F 分组。每条给现象、证据位置、以及「缺的是什么」。**A–F 的正文保持写作时原貌，
未逐条改写**；闭环与否以「闭环状态」节为准。

> 分组状态一览（2026-10-14）：**A 定位与留存**——A2/A3/A4 已闭环，A1/A5 未做，A6 部分；
> **B 前端功能设计**——全部为 P2，未做（B3 部分）；**C 后端功能设计**——C3/C5 已闭环，
> C1/C2/C4 未做；**D 前后端契约**——全部为 P2，未做；**E 用户体验**——E1~E9 已闭环；
> **F 产品功能面**——F1 已闭环，F2/F3 部分，F4/F5/F6 未做。

## A. 定位与留存

### A1 · 间隔复习引擎叫不醒用户

复习到期提醒只存在于站内；站外触达（短信/微信）在 phase 1 被明确列为 out of scope，
WebSocket 又是 best-effort。也就是说，**核心留存机制依赖的触发器，在 App 关闭时就不存在**。
间隔复习本身做得越精细，这个缺口越可惜——算法算出了「今天该复习」，却没有任何通道把用户叫回来。

**缺的是**：一条站外提醒通道（或至少把 WebSocket 定位成「在线时的优化」，并补一个可靠的补偿轮询）。

### A2 · 新用户靠「撞」上魔法时刻

路径是：海报 → 注册 → onboarding → 首页。新用户的首页 = 问候语 + 三个 0 + 一个网格，
没有示例视频，没有一句差异化说明。2026-08-30 的决策明确跳过了新用户 demo 视频。

结果是：用户注册后的第一屏，什么都证明不了。产品的差异化（视频里点词、词级高亮、句子跟读）
要自己摸索才能碰到。

**缺的是**：首次进入时的「第一课」——一段 30–60 秒的示例视频，或一条被引导完成的最短闭环。

### A3 · 跳过 onboarding 会静默关掉核心功能

`target_exam=null` 会让考试词高亮直接关闭，这是旗舰功能，但跳过后没有任何提示说明后果；
重新开启的入口埋在设置和播放页顶栏里。用户做了一个看似无害的「跳过」，代价是产品最值钱的
能力被关掉，而他永远不会知道。

**缺的是**：跳过时的明确代价提示，以及一个可被发现的「随时回来设置目标」入口。

### A4 · 闭环终点没有奖励

里程碑只有：词汇量 50/200、掌握 100、连续 7/30 天、看满 10 个视频、首次复习/跟读。
**没有「第一组词刷完」「某个视频的词全掌握」这类贴合闭环节点的奖励**。从筛词到 100% 掌握
的整个过程，没有任何庆祝点。

内测文案「刷完一集剧，顺手拿下 28 个四级词」在产品里没有落点——用户完成了这个动作，
产品不会告诉他这件事发生了。

**缺的是**：以「一集剧 / 一组词」为单位的完成奖励与可分享的成就卡。

### A5 · 没有考试目标的叙事

`target_exam` 目前的作用只是给词上色。没有核心词覆盖率、没有目标词量、没有考试倒计时、
没有「你现在覆盖了四级核心词的百分之多少」。PRD 里「不派任务」被正确地执行了，但
**不派任务 ≠ 不给目标**。用户看不到自己在接近目标，就只剩下一集一集地看。

**缺的是**：一条围绕考试目标的进度叙事（覆盖率 / 词量 / 倒计时三选一即可）。

### A6 · 付费模型出现两份互相矛盾的文档

PRD v3.0：Free 与 Pro 的差别只在解锁数量。
内测需求 v1：Pro = 效率与深度（无限集合、进阶算法、跟读配额、去广告）。

两份文档对「Pro 卖什么」给出不同答案，而内测到正式上线的切换没有被设计过。

**缺的是**：一次明确的付费模型拍板，以及内测权益到正式权益的迁移规则。

## B. 前端功能设计

### B1 · 服务端状态没有主人

30+ 个 hook 各自 `useEffect + useState` 拉数据；手写缓存在
`frontend/src/lib/createApiClient.ts`（按 URL 做 TTL、GET 去重、任何非 GET 请求清空整个缓存）。
没有失效图，没有乐观更新的统一原语，每个页面的乐观删除都是手写一遍。

**缺的是**：一个服务端状态的单一持有人（TanStack Query 之类），让缓存、失效、乐观更新有共同语义。

### B2 · 会话有两个真相源

token 的真身在 localStorage，同时镜像进 cookie 供 `frontend/src/proxy.ts` 使用；
过期、刷新、解码在客户端各做一遍。用户侧 `authStore` 与管理端 `adminAuthStore` 平行存在。
`mediaUrl()` 把长期 bearer 放进 `<video>/<audio>` 的 query string，代码注释自己承认
「不得写进日志/分享链接」——一个需要靠注释约束的凭据传递方式。

**缺的是**：会话状态的单一真相源，以及媒体访问的安全替代（短期签名 URL）。

### B3 · 偏好域被切成三份

localStorage 存了字幕模式、教练开关、搜索历史、主题、`onboarding_completed`；
后端有 `user_preferences`；store 里还有一批标志位。其中
`onboarding_completed` 同时存在于后端 `User.onboarding_completed` 和 localStorage，
两边可以漂移。

**缺的是**：每个偏好一个明确的家，跨设备需要同步的进后端，纯本地的才留 localStorage。

### B4 · App Router 被当作 SPA 用

几乎每个页面都是 `"use client"`，数据全部在客户端拉，没有 Server Components、
没有流式渲染、没有路由级 loading。代价是请求瀑布：壳层先到、数据后到、首屏内容再后到。

**缺的是**：一次有选择的服务端渲染下沉，至少在只读的列表/详情页。

### B5 · 文案硬编码

所有文案直接写在组件里。当前只有中文，一旦要做多语言或统一改语气，
就得逐组件搜。

**缺的是**：一层文案抽取（不必上完整 i18n 框架，但需要一个可集中修改的位置）。

## C. 后端功能设计

### C1 · 错误分类只做了一半

`backend/app/core/errors.py` 有完整的错误码体系，但 `backend/app/api/v1` 里
**176 处 `HTTPException` 对 11 处 `AppError`**。绝大多数失败路径返回泛化的
`HTTP_404` / `HTTP_403`，前端无法据此区分「不存在」和「无权看」。

**缺的是**：把错误码体系真正铺到 API 边界，至少覆盖用户可感知的失败分类。

### C2 · 活的契约里带着死功能

`learning_plan.py` 的 9 个端点全部返回 410；`/videos/unlocks` 返回空分页；
`mock_payments` 靠环境变量挂载。同时 comments / proposals / learning_plan / orders /
redeem / unlock 这些 model 仍注册在 `backend/app/models/__init__.py`。

没有「能力清单」，判断「支付开没开」要同时看 `settings.payments_enabled`、
路由挂载、前端跳转和文档四处。

**缺的是**：一份能力清单（capability manifest），让「这个环境有什么功能」只有一个出处。

### C3 · 实时推送是单进程的

`backend/app/api/v1/notifications.py` 里的 `ws_manager` 是模块级 dict，
而生产是 Gunicorn 多 UvicornWorker（见 `docker-compose.prod.yml`）。
Worker A 无法推送到 Worker B 持有的 socket；前端 `NotificationDropdown` 一旦
WebSocket「已连接」就停止轮询，于是跨 worker 的通知会被静默丢掉。

对照组是 `presence.py`，它正确地走了 Redis。同一个仓库里已经有正确答案。

**缺的是**：把 WS 广播也搬到 Redis（或退回轮询），并让前端在 WS 之外保留兜底刷新。

### C4 · 边界过载

`videos.py` 有 **49 个端点**。几个大的 service：`subtitle_edit` 32KB、
`video_service` 28KB、`admin_service` 27KB、`practice` / `vocab_set` 各 25KB。

**缺的是**：按资源与生命周期拆分路由和 service（这属于结构性清理，不是紧急缺陷）。

### C5 · 账号注销与数据导出没有端点

全仓 0 处实现。对手机号注册的产品，这是合规与信任层面的硬缺口；
叠加 71 个迁移和长期休眠的表，账号生命周期目前是不完整的。

**缺的是**：注销（含数据处理策略）与数据导出两个端点。

## D. 前后端契约

### D1 · 没有 OpenAPI → TS 代码生成

`frontend/src/types/index.ts`（约 20KB）是手写的，对应约 190 个端点；没有漂移检查。
后端改字段、前端不改，类型照样通过。

**缺的是**：从 OpenAPI 生成前端类型（或至少加一个契约漂移检查）。这是全项目
**结构性收益最高的一项改动**。

### D2 · 没有功能能力清单

见 C2。前端需要靠零散的重定向、env 和约定推断「这个部署开不开支付/学习计划」。

**缺的是**：后端暴露一份能力清单，前端据此渲染，而不是各自猜。

## E. 用户体验

### E1 · 注册是漏斗最大漏点，且与宣传打架

`frontend/src/app/register/page.tsx` 要求：手机号 + 短信验证码 + 设置密码
（≥8 位、含大小写与数字）+ 确认密码 + 同意条款。而海报写的是「扫码就能进」。

同时 `login/page.tsx` 只提供手机号 + 密码，但 PRD §3.2 说验证码或密码都可以——
忘记密码只能走三步重置。

**缺的是**：免密注册/登录（验证码即登录），把「设置密码」变成可选的后置动作。

### E2 · 新用户先看到首页，再被拽去 onboarding

注册成功后 `router.replace(next)` 直接去首页；`frontend/src/app/(main)/MainLayoutInner.tsx`
里注释写着「Render shell immediately — onboarding check runs in background」，
然后异步拉 `/users/me` 才重定向到 `/onboarding`。

用户会先看到一个空首页闪一下，再被弹走。

**缺的是**：把首次进入的路由决策放到渲染之前，或者让首页承担 onboarding 的职责。

### E3 · 跳过 onboarding 会静默关闭差异化功能

同 A3。这是用户体验问题，也是定位问题：产品最独特的考试词高亮，
因为一次「跳过」被关掉且无告知。

### E4 · 导航信息架构两端不一致

桌面 TopBar：首页 / 频道 / 练习专题 / 单词训练 / 学习记录。
移动端 MobileTabBar：首页 / 频道 / 练习 / 单词训练 / 我的。

→ 学习记录只有桌面有；我的只有移动有；收藏只在头像菜单里；
完整榜单藏在首页排序下拉的最后一行。

**缺的是**：一套两端一致的导航主干，以及明确「哪些功能放二级」的规则。

### E5 · 点词看释义会盖住当前句

INV-022 把这个记为「已接受的代价」：词卡顶边正好等于画面底边，
因此完全遮住当前句卡（句子 + 计数器 + 展开）。这与「在语境里学词」的卖点直接冲突——
查一个词的那一刻，语境消失了。

**缺的是**：词卡与当前句共存的布局（例如词卡只占下半屏，或当前句上移）。

### E6 · 训练每答一题都要手点「下一个」

`frontend/src/components/.../WordFlashcard.tsx` 的注释说明这是刻意设计（§4.2）。
但每天 20–50 题的练习题量下，就是几十次额外点击；没有「答对自动前进」的开关。
同时头部并存两套进度语义（「第 N 题」与按词计的 done/total）。

**缺的是**：一个「答对自动前进」选项，以及统一后的唯一进度语义。

### E7 · 搜索占位符承诺了做不到的事

占位符写「搜索视频、字幕、单词…」，但后端只有 `search_videos`（标题/标签）
与 `search_subtitles`，**没有词汇搜索**。

**缺的是**：补上词汇搜索，或把占位符改成真实能力。

### E8 · 公开帮助页挂了私人邮箱

`frontend/src/app/(main)/contact/page.tsx` 展示 `1841666301@qq.com`。
对外页面应使用域名邮箱或工单入口。

### E9 · 账号级体验缺失

同 C5：没有注销、没有数据导出。用户在「我的」里找不到任何账号收尾能力。

## F. 产品功能面

### F1 · 目标用户是四六级，考试功能只覆盖阅读

`backend/app/services/exam_service.py` 的 `SECTION_ORDER` 只有
`reading_A / reading_B / reading_C`。四六级听力约占 35%，写作与翻译完全缺席；
「听力」只作为词汇题的一个类型存在。

这是**最大的功能洞**：要么补听力（至少让听力词汇有独立训练面），
要么把定位收窄为「词汇 + 阅读」。当前状态是对外宣称一套、产品交付另一套。

### F2 · `target_exam` 只用来染色

同 A5。设置项存在，但除了给词上色没有产生任何用户可见的目标感。

### F3 · 功能不少，发现性不均

收藏、笔记、历史、周报分享卡、完整榜单、里程碑、事件分布都已实现，
但散落在头像菜单、排序下拉、个人页三个 tab 里。做完了不等于用户找得到。

**缺的是**：一次功能发现性盘点，把已建成的能力放到用户会经过的路径上。

### F4 · 内测运营机制几乎不在产品里

「7 天打卡挑战」「创始会员徽章」「反馈换上线权益」都没有产品载体，
全靠微信群人工运营。内测期可以接受，转正式前需要落成产品机制。

### F5 · 提醒功能做完了，触达通道没做

同 A1 / C3。通知中心、WS 推送、提醒设置都有，唯独缺「用户不在线时怎么办」。

### F6 · 多个平行进度指标，缺统一叙事

掌握度环、到期角标、连续天数、里程碑、周周期、事件分布——六个指标各说各话，
用户可以同时看到六个进度，却不知道「我现在到底怎么样」。

**缺的是**：一个主导航层面的主指标，其余降为支撑证据。

## 已经很好、应当保护的部分

这份总结是「缺什么」，但下面的东西不要在做改动时弄丢：

- **移动端播放页的几何与真机基线**（INV-019 ~ INV-025）——把控制搬进壳层、
  当前句三行带、单层滚动，这些是反复打磨过的。
- **训练调度器**——两次答对毕业、题型轮换、错题分层间隔。
- **空态/错误态/加载态的完整覆盖**，以及带 Undo 的乐观删除。
- **统一错误信封 + Redis fail-open** 的基础设施。
- **`knowledge/` 冷仓 + ADR + 认知层**：文档纪律本身是这个项目的资产。
- **管理后台的完整度**——字幕编辑器、内容池、频道、反馈、统计。

以及功能面与目标用户的错位**——都是产品取舍，不是工程难题。
