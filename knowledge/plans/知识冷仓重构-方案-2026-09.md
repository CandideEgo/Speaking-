# 知识冷仓重构 — 方案（2026-09）

> 制定日期：2026-09-29 ｜ 状态：**执行中**（分支 `refactor/knowledge-cold-store`）
> 事实来源：本仓 tracked 文件逐处扫描（知识性 markdown 99 个 / 约 994 KB，不含 `docs/design/`），
> 以及 `scripts/check-knowledge/check_knowledge.py` 的常量表逐条核对。本文件是**设计记录**：
> 它按定义要写旧路径，是搬迁时唯一不被路径重写的知识文件。
> 边界：只动文档、配置与检查器。不动任何业务代码（`backend/`、`frontend/` 的逻辑行一律不碰）。

---

## 0. 结论先行

1. 现在的问题不是「知识太多」，是**没有分层**：每会话必读的 65 KB、只在出事时才查的 200 KB 归档、必须逐条追溯的决策正文，三样挤在同一套目录与同一套体积规则里。
2. 体积规则是这个混乱的症状，不是解药。字节上限在**写入那一刻**生效，最省事的应对永远是「把话说短一点」或「干脆不写」——两种损失没有任何检查看得见。本方案**取消一切字节上限与字节目标**，改用一套分层标准。
3. 目标结构三句话：**热层极小且只放「现在为真」的事实；冷仓一个目录、按需查；中间加一层可机检的索引**，保证冷仓不变成遗忘。
4. 搬迁的最大风险不是文件搬错，是**改名让检查静默失效**：八道门里有六道靠路径前缀判断，改名前缀一扫不到文件就全通过，CI 绿而门已死。所以顺序是先让检查器「配置驱动 + 路径不存在即失败」，再搬文件。

---

## 1. 现状：三层其实住在一个平面里

| 实际用途 | 现在住哪 | 体量 |
|---|---|---|
| 每会话必读 | `AGENTS.md` + `.agent/` 的 8 个文件 | 65,645 B |
| 改代码前的硬约束 | `.agent/invariants.md`、`.agent/system-map.md` | 12,998 B（含在上行内） |
| 决策正文（append-only，必须能逐条追溯） | `.agent/decisions.md` + `decisions-index.md` | 32,252 B |
| 长期工程知识 | `wiki/` | 21 个 / 99,213 B |
| 已落地的方案与进度 | `docs/plans/`、`docs/progress/` | 18 个 / 359,098 B |
| 接口与部署的历史事实 | `docs/operations/`、`docs/requirements/` | 7 个 / 121,151 B |
| 架构决策记录（点时刻，不可改） | `docs/adr/` | 18 个 / 82,990 B |
| 已关闭的票与旧决策正文 | `.agent/archive/` | 15 个 / 217,840 B |
| 口播原话（封存，不可编辑） | `inbox/` | 3 个 / 7,682 B |
| 变更日志 | `CHANGELOG.md` | 40,844 B |

四处毛病：

1. **「每会话读」和「出事才查」用同一套规则定价**，于是 200 KB 的归档在体积表里和热层文件是同一种东西。
2. **沉淀知识有两个家**（`wiki/` 与 `docs/`），判据是「当初是谁写的」而不是「多久读一次」。
3. **`.agent/` 同时装着热层事实（state/invariants）与历史档案（archive/decisions）**，名字上分不出来。
4. **索引不可信**：`wiki/INDEX.md` 手写维护二十来条，`decisions-index.md` 与正文必须逐条对应。两份索引都在人手底下，机器只校验了后者。

## 2. 目标结构

### 2.1 热层（每会话读，必须「当且仅当现在为真」）

| 文件 | 装什么 | 为什么必须热 |
|---|---|---|
| `AGENTS.md` | 路由表 + MUST / SHOULD / NEVER | 唯一的入口 |
| `CLAUDE.md` | 3 行重定向 | 工具入口，不动 |
| `CONTEXT.md` | 领域术语表（真身；原 `.agent/context.md` 并入，删掉那层指针） | 读代码、写需求都要 |
| `.agent/README.md` | **分层标准**：哪条知识放哪层、索引契约、写入规则 | 写知识时的规则本身 |
| `.agent/state.md` | 在飞的事 / 下一步 / 已知问题 | 决定今天做什么 |
| `.agent/invariants.md` | 硬约束 | 改代码前的红线 |
| `.agent/owners.md` | 切片、票、并行纪律 | 派活时的规则 |
| `.agent/handoffs/*.md` | **未关闭**的票 | 交接本身 |

热层准入三条，**全部满足**才留：

1. 每个会话都要读它，与今天做什么无关；
2. 它描述的是**现在**，不是过去（凡有「曾经」「已修复」「历史」字样即不合格）；
3. 读它是为了决定**下一步动作**（不是为了理解某个已完成的决定）。

### 2.2 冷仓 `knowledge/`（一个目录，按需查）

| 新位置 | 从哪来 | 说明 |
|---|---|---|
| `knowledge/INDEX.md` | 新写（并吸收 `wiki/INDEX.md`） | 入口索引，见 §2.3 |
| `knowledge/decisions.md` | `.agent/decisions.md` | append-only，不改内容 |
| `knowledge/decisions-index.md` | `.agent/decisions-index.md` | 与正文逐条对应 |
| `knowledge/system-map.md` | `.agent/system-map.md` | 模块连接图 |
| `knowledge/wiki/` | `wiki/` | architecture / problems / guides |
| `knowledge/adr/` | `docs/adr/` | 点时刻记录，不可改 |
| `knowledge/plans/` | `docs/plans/` | 含本文件；已落地方案也留在这（不销毁） |
| `knowledge/progress/` | `docs/progress/` | |
| `knowledge/requirements/` | `docs/requirements/` | |
| `knowledge/operations/` | `docs/operations/` | |
| `knowledge/archive/` | `.agent/archive/` | 含 `archive/handoffs/`，已关闭的票 |
| `knowledge/inbox/` | `inbox/` | 封存的原话，检查器豁免链接校验 |
| `knowledge/CHANGELOG.md` | `CHANGELOG.md` | 变更日志就是历史，按用户原话进冷仓 |

### 2.3 索引层（冷仓不变成遗忘的唯一保证）

`knowledge/INDEX.md`，一份文件，**每个文档一行**：

```
- 路径 — 一句话（取 frontmatter 的 title，或文档第一个标题）— 状态/日期（有则写）
```

按子目录分组，组内按日期倒序。它是人工可维护的目录页，不是生成物——但**双向一致性由机器检查**：

- `knowledge/` 下每个文件（`archive/` 除外）在 `INDEX.md` 里**恰好一行**；
- `INDEX.md` 里每个路径都**真的存在**。

两句话都成立，才叫「需要的时候查得到」。只做前者会漏登记，只做后者会留下死链。

### 2.4 刻意留在原地

| 位置 | 为什么不动 |
|---|---|
| `docs/agents/` | 技能读的固定路径：`setup-matt-pocock-skills` 等按约定往这里写 `issue-tracker.md` / `domain.md`。搬走等于下次重跑技能时生成重复文件。 |
| `docs/design/` | 物料不是知识：海报、HTML 原型、发布图。没人靠读海报改代码，它不参与知识层的链接与分层规则。 |
| `backend/` `frontend/` | 业务代码。本次一行逻辑都不改。 |

于是 `docs/` 的语义收敛为一句话：**`docs/` 只放「工具按固定路径找的文件」与「物料」，凡是我们写给自己的知识都在 `knowledge/`。**

## 3. 用标准取代上限

**新规则：知识层没有任何字节上限，也没有字节目标。** 机器只报数（`--size-report` 打印热层各文件与冷仓各子目录的体积），不判定、不拦人、不产生「留给下次收敛」的欠账。

替代它的是一套**写下时就分层**的标准（真身在 `.agent/README.md`）：

1. 写之前先问：这条事实**现在为真**吗？是 → 热层；描述过去 → 冷仓。
2. 冷仓里的每条事实必须在 `knowledge/INDEX.md` 有一行；没登记就等于没写。
3. 一条事实只有一个家。热层写「结论 + 指路」，细节在冷仓，两边不重复。
4. 事实从「现在」变成「历史」时**搬，不删**——搬进冷仓，登记一行。
5. 取消周期性压缩轮（`/knowledge-maintain` 不再为了压体积而跑）。分层在写入时完成，过期内容靠「搬」而不是靠「删」。

为什么这样比上限好：上限管的是**一句话写多长**，标准管的是**一条事实放哪**。前者可以靠删字作弊，后者作弊就会被索引双向检查抓住。

## 4. 检查器改造：先让门不会静默失效

现状：八道门里，`frontmatter`、`ownership`、`stale`、`captures`、`handoff`、`index` 都靠**路径前缀或写死的文件名**判断扫哪些文件。改名之后它们扫不到东西就全通过——`[ok]` 是空集上的 `[ok]`。会立刻变红的只有 `index` 与 `layout` 两道。

三步改造（先做，后搬）：

1. **`scripts/check-knowledge/paths.json`**：所有知识路径集中到一份配置，检查器改为读取它。改名的动作从「二十处字面量」变成「一处配置」。
2. **配置里的路径不存在 ⇒ 检查失败**（新增）。这是防静默失效的正解：改名而忘了改配置，会红，不会静默变绿。
3. **删掉字节上限**：`knowledge-budget.json`、`budget` 门、`--budget-refresh` / `--budget-report` 全删；换成只报不判的 `--size-report`。`index` 门的双向检查扩到 `knowledge/INDEX.md`。

其余同步修改：`modules.json` 的 `knowledge-layer` globs、`layout.json` 的顶层条目表、`.pre-commit-config.yaml` 的触发正则。

**搬迁纪律：每批搬完，必须对照「改名前后 checker 扫到的文件数」**，因为静默失效是本任务最大的隐藏风险，而它恰好是「CI 绿」看不出来的那一种。

## 5. 搬迁顺序（每阶段可回滚）

| 阶段 | 内容 | 完成判据 |
|---|---|---|
| 1 | 检查器配置驱动 + 路径不存在即失败 + 删上限 | 现树仍全绿 |
| 2 | `git mv` 冷仓目录 + 全仓路径前缀重写 | 检查器扫到的文件数与阶段 1 一致 |
| 3 | 写 `knowledge/INDEX.md` + 双向检查 | 索引双向检查通过 |
| 4 | 热层瘦身：`.agent/context.md` 并入根 `CONTEXT.md`；`AGENTS.md` 分层表收敛为指针；`.agent/README.md` 改写为分层标准 | 热层只余 §2.1 名单 |
| 5 | 重签 `stale` stamps 与 baseline；跑全量检查 + pre-commit | 全绿 |

回滚：全程在一个分支上，每个阶段一个提交；`master` 在合并前不动。

不可改的历史引用（刻意不修）：

- `backend/migrations/versions/` 三个迁移脚本 docstring 里的 `docs/plans/PIPELINE-RESUME-DEDUP-AUDIT.md`——迁移脚本修改等于重写已应用的迁移，且该文件早已不存在（见 §6）。
- `knowledge/archive/` 内部：既成历史的记录不追认今天的链接与格式。

## 6. 代价与不做的事

- **代价**：全仓链接一次大搬迁；`paths.json` 成为新的单点（忘记维护它会让门变红——这是故意设计的方向）。
- **不做**：不删任何知识文件（体积从来不是目标，找不到才是）；不改 `docs/plans/` 已落地方案的归属；不动业务代码；不给热层设「≤N KB」这类换汤不换药的上限。
- **已知腐坏（本次只是不再掩盖）**：`docs/plans/PIPELINE-RESUME-DEDUP-AUDIT.md` 被 8 个文件引用而文件已不存在。搬迁后这些引用指向 `knowledge/plans/` 的同一缺失文件；要么补回文件，要么在索引里标为已销毁，留待下一轮决定。
