## 1. 问题陈述

用户的原始表述：

> 「我这边给需求了，搞出来后怎么让下一个 Agent 执行？要给它打标签还是什么？没有技能去调用它，也没有东西去进行交接。」

这句话精确指出了现状的空洞：**没有推送机制，也没有查询机制**。`knowledge/inbox/` 的 `triage.md` 里 `execute` 段的「去向」写的是 `knowledge/plans/` 或 `.agent/owners.md`——那是把地址写在纸上，不是把东西送到。中间没有东西负责「判定它是哪一种」「切成一票一票」「让下一个 agent 知道该拿哪张」「跑完了谁认账」。

而「打标签」只是四件事里最不重要的一件（见 §2.4）。

## 2. Matt 侧的机制（已从源码核实，不是二手描述）

### 2.1 技能是指针，不是流程

它的 skill 定义（`aihero.dev` 的 AI Coding Dictionary 条目）：

> A teachable capability bundled as a unit — instructions and resources for doing one task well, kept in the **environment** until a **context pointer** pulls it into the context window for the task at hand.

所以官方技能极短，这是设计而非偷懒：`wait-what/SKILL.md` 三行；`handoff/SKILL.md` 16 行；`implement/SKILL.md` 15 行；`grill-with-docs/SKILL.md` **只有一行**，把活全派给 `grilling` + `domain-modeling`。

两个负荷（`skills/productivity/writing-for-agents/SKILL.md` 原文）：

- **context load**：每回合都在花的 token 与注意力（AGENTS.md 的一行、一个技能描述）。
- **cognitive load**：压在**人脑**上的成本——记住有哪些文档、什么时候该用哪个。「The human is the index.」

关键推论：**没有指针指向的资料，成本 100% 压在认知负荷上**（"material with no pointer at all rides entirely on cognitive load"）。

**对本仓的直接含义**：把流程写进技能正文，等于每个回合都付一遍 context load。`/intake` 目前 84 行，方向是反的；将来缝 1–4 的实现要短，长的那部分推成技能系统外的普通文件。

### 2.2 调用模型决定系统拓扑（最深的一条）

每个技能声明自己是 user-invoked 还是 model-invoked（`SKILL.md` 里 `disable-model-invocation: true`，Codex 侧由 `agents/openai.yaml` 的 `policy.allow_implicit_invocation: false` 配对）。硬规则（`.agents/invocation.md` 原文）：

> A user-invoked skill may invoke model-invoked skills, but it can never reach another user-invoked skill.

推论极狠：**两个 user-invoked 技能都要用的共享资料，不能住在任何一个技能里，必须推成技能系统之外的普通文件**，谁都能指它。这就是为什么它有一层 `docs/agents/*.md`，为什么技能正文短得离谱——共享的东西全在技能外面，技能里只留「去哪读、什么时候读」。

**这直接回答「怎么把它们交互起来」**：

1. 共享事实推到技能外部的普通文件（本仓已有这一层，见 §3.2）；
2. 需要被别的阶段调用的阶段，保持 model-invoked；
3. 其余用显式点名调用：`Call the Skill tool with "grilling"`，**且去掉 name 前的斜杠**——去斜杠才不绑定某个 harness 的触发语法；
4. 一次只调一个（"The Skill tool takes one skill per call"），需要两个就写两次调用。

### 2.3 同一张图用了四次

| 层 | 节点 | 边 | frontier | 认领 |
|---|---|---|---|---|
| grilling | 问题 | 「依赖一个未决答案」 | 现在就能问的问题 | — |
| 票 | 垂直切片 | `Blocked by` | 阻塞项全关的票 | assignee |
| wayfinder 地图 | 决策票 | 原生 blocking | 打开、未被挡、未被认领 | assignee |
| 会话 | 阶段 | 上下文依赖 | — | continue / clear / handoff / subagent / compact |

`frontier` 这个词被**故意重复**（leading word：借模型预训练里已有的词，重复它 = 用最少 token 锚定一整片行为）。所以「编排」不是流程图，是**依赖图上只推进 ready 的那一层**。

### 2.4 状态住在工单的字段里

| 问题 | 谁回答 | 机制 |
|---|---|---|
| 该不该做 | 边 | 阻塞项全关了吗 |
| 有没有人在做 | 锁 | `gh issue edit <n> --add-assignee @me`——"the assignee **is** the claim" |
| 什么状态 | 标签 | `needs-triage` / `needs-info` / `ready-for-agent` / `ready-for-human` / `wontfix` |
| 我该拿哪张 | 查询 | frontier query：列出打开的子 issue，丢掉有打开阻塞项或已有 assignee 的，取地图顺序里第一张 |

**`Close` 是解锁动作。** frontier 的定义是「阻塞项全关」，所以没人关票 = 没有任何东西会变成可开工。

### 2.5 它自己承认的弱点（必须一起借，否则会重犯）

- **`implement` 不关票**：「It has no completion step... Close the ticket and reconcile the criteria yourself.」这是全流程最大的手工步骤。
- **同一个 checkout 里并行跑多个 `/implement` 会互相破坏**：一次事故里「一个 session 的 `git commit --amend` 落到另一个 session 的 commit 上、`refs/stash` 里的东西消失、commit 落到错分支」。社区绕法是 worktree，但 `refs/stash` 在 worktree 之间仍共享。
- **没有自动派发**；`to-tickets` 原话：「produces the artifact; running it (one session at a time, or a fleet) is your job, not the skill's.」
- **router 只能提示不能触发**（`ask-matt` 自己是 user-invoked），所以「新技能它没提，或旧技能它还在导」= 一个会撒谎的路由。

**对本仓的含义**：`.agent/owners.md` 规则 4（≤2 并行、禁用 worktree）方向是对的，不要为了「更完整」去解禁。

- S1–S8 就是按这个跑完的。

**这已经是一个票系统了。**它缺的不是形状，是连接件。

### 3.3 缺的四样（grep 证据）

`.agent/` 全域 grep `Blocked by|blocked_by|frontier|阻塞|依赖图`：命中的全是业务语义的「阻塞」（如 `state.md:20` 的母带删除被阻塞）或归档文件，**没有任何一处是票与票之间的依赖边**。

| 缺什么 | 今天的实际后果 |
|---|---|
| **边** | handoff 模板没有 `Blocked by`。依赖只能手写在计划正文的箭头图里（`knowledge/plans/词汇训练与播放页返回-剩余分片计划-2026-09.md` §1.1），机器看不见，改一次要改两处 |

## 4. 四道缝的规格

```
口播原话 ─[有]→ raw.md ─[有]→ triage.md（一段一行）
                                  │
                    缝1  段 → 决策 / 方案 / 票（谁判定它是哪一种）
                                  ▼
                    缝2  方案 → 票（垂直切片 + 边 + 验收 + 演示路径）
                                  ▼
                    缝3  票 → frontier 查询 → 认领（下一个 agent 怎么知道自己该干哪个）
                                  ▼
                    缝4  执行 → 交接 → 验收 → 关闭（关闭才是解锁下一个的动作）
```

**缝 1 — 段归位。** 输入是 `triage.md` 的一行（`decide` 或 `execute`），输出是一个真实去处。判定规则按现有 DEC 纪律：不可逆/架构/选型 → `decide` → 走 `/decision-support` 出 `DEC-0xx`；其余 → `execute` → 进方案。**产出的「去向」必须是可被机器解析的标识**，不能是散文地址。

**缝 2 — 方案切成票。** 按 Matt 的垂直切片四条（每条裁一条穿过所有层的**窄而完整**的路径、单独可演示、**能塞进一个上下文窗口**、预重构先行）+ 本地已有约束（owner 边界、契约文件）。票必须带四样：`Blocked by`、`Planner acceptance`（已有）、`演示路径`（拒绝水平切分的唯一抓手）、`Owner`。
- 尺度判据用**「能塞进一个上下文窗口」**而不是行数；Matt 对「agent 烧了 150k token」的回答是「Probably the ticket is too big rather than the skill being misused」。
- 票体**不要贴文件路径和代码片段**（会腐烂），唯一例外是把决策表达得比散文更准的片段（状态机、reducer、schema、类型形状）。

**缝 3 — frontier 与认领。** 一条查询（本地 markdown：解析 `handoffs/*.md` 的三行字段）＋ 一次认领（写 `Owner`）。规则：打开、阻塞项全关、无 `Owner` 的票 = 可拿；按依赖顺序取第一张。

**缝 4 — 交接、验收、关闭。** 执行者写四节（已有）；planner 机械验收（已有）+ 契约 diff（已有）；**新增的是关闭动作**——`Status: done` 之后要显式关闭并在 `state.md` 记录，否则下游不释放。另需一个 adopter：验收者**不能是**执行者。

## 5. 三条路线

| | A 本地 markdown 队列（推荐） | B GitHub Issues 原生 | C 混合 |
|---|---|---|---|
| 队列 | `.agent/handoffs/` 升级 | Issue + label + assignee | 本地为机器面，`ready-for-human` 才开 Issue |
| 边 | `Blocked by:` 行 | native issue dependencies（`gh api .../dependencies/blocked_by`） | 同 A |
| 锁 | `Owner:` 行 | assignee | 同 A |
| frontier | 一个脚本/检查 | `gh issue list` + 过滤 | 同 A |
| 好处 | 与现有实践同构（S1–S8、分片计划、owners、handoffs 都是本地 markdown）；离线；**可进 `check_knowledge.py` 被机器强制** | 跨机器、可视化、可见性由 GitHub UI 免费提供 | 保留手机可读 |
| 代价 | GitHub Issues 那条线要明确降级为「只收 bug 的箱子」，或承认它是空的 | 每次都要 gh；子 issue 与依赖边 API 在 Matt 那边本身挂着 open bug；Issue 目前不是本仓工作面；**无法被本仓检查器强制** | 两处状态要同步，得先定谁是真源 |

**推荐 A**：本仓已在这条路上；Matt 的 GitHub 那套是给「多人多机、要看板子」设计的，本仓是单机 + ≤2 agent；而**本地 markdown 能进 `check_knowledge.py`**——Matt 那套最大的弱点恰恰是没人强制（§2.5），这一点本仓可以直接补上。真正该借的是**模型**（节点/边/frontier/认领/关闭）与**纪律**（技能短、共享资料出技能系统、不用否定式提示），不是它的机器。
